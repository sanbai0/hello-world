# 策略模式实战：按协议族复用渠道实现

接入三个外部服务，不一定需要写三个适配器。真正决定代码能否复用的，是请求签名、数据结构和交互步骤，而不是服务商的名字。

以一个物流查询平台为例：甲、乙两家物流商购买了同一套 SaaS，查询接口都使用协议 P；丙自建系统，使用协议 Q。平台对外只提供“根据运单号查询轨迹”。若按公司名称复制实现，甲、乙的代码很快就会出现只有地址、商户编号不同的重复。

策略模式在这里解决的核心问题，是让调用方只依赖稳定能力，同时让协议差异集中在对应实现里。

## 先把三种变化拆开

| 变化 | 物流示例 | 合适的位置 |
|---|---|---|
| 接入身份变化 | 商户编号、服务地址 | 渠道配置 |
| 协议变化 | 签名算法、字段映射 | 策略实现 |
| 业务能力变化 | 查询轨迹、创建运单 | 能力接口 |

这张表能回答一个很实际的问题：接入第四家物流商时，究竟该新增一条配置，还是新增一个类？如果只是协议 P 的另一位租户，增加配置即可；如果连签名和交互顺序都不同，就应提供新的策略。

![渠道配置映射到协议策略，再输出统一轨迹结果](博客公开附件/工程实践/策略模式实战-按协议族复用渠道实现.png)

注册关系可以表达成“渠道 → 协议族 → 实现”。渠道配置负责找出协议类型，策略注册表负责找到实现，主流程负责组合二者。

```java
record ChannelContext(String channelId, URI endpoint,
                      String merchantId, String credentialRef) {}

interface TrackingStrategy {
    TrackingResult query(ChannelContext channel, String trackingNo);
}

TrackingResult query(String channelId, String trackingNo) {
    ChannelConfig config = channels.require(channelId);
    TrackingStrategy strategy = strategies.require(config.protocol());
    return strategy.query(config.toContext(), trackingNo);
}
```

这里刻意把 `ChannelContext` 放在方法参数里。策略对象可以是长期复用的单例，渠道地址和商户身份则属于本次请求。两个请求分别访问甲、乙时，各自携带自己的上下文，不需要先修改策略对象上的 `currentChannel` 字段。

“先设置渠道，再执行查询”看起来只多了一步，却把正确性依赖放在了调用顺序上；显式参数把这种依赖直接写进方法签名。共享对象保持无状态，也让并发测试更容易构造。

## 统一的是含义，不是外部字段

协议 P 可能返回 `delivered: true`，协议 Q 可能返回状态码 `90`。主流程不应认识这些差异。两个策略都应转换为统一的 `DELIVERED`，同时保留必要的外部引用，方便追查。

错误也需要同样的整理。“没有查到运单”和“鉴权失败”不能都转换成空列表。前者是正常业务结果，后者意味着请求没有获得有效答案；如果调用方区分不了，就可能把一次鉴权故障显示为“暂无物流”。

统一结果可以包含业务状态、轨迹列表和明确的错误类别。协议特有的响应结构留在适配层，避免字段名逐步泄漏到业务代码。

## 注册阶段就发现接入错误

策略注册不只是把几个对象塞进 Map。启动时可以核对三项约束：协议名不可重复、已启用渠道必须找到实现、必要配置必须完整。这样，错误会在发布验证阶段暴露，而不是等某个用户第一次选择冷门渠道时才出现。

未知协议也不宜自动落到某个默认实现。只有协议本身确实支持通用行为时，默认策略才有意义；否则，明确报出“协议未注册”比远端返回一个难懂的签名错误更有帮助。

## 不把可选能力塞成空方法

假设协议 P 支持取消运单，协议 Q 只支持查询。让 `cancel()` 默认返回 `null`，会迫使主流程猜测这是“不支持”，还是“取消失败”。更明确的选择是拆出 `CancellationStrategy`，或者返回独立的能力描述，并在执行前校验。

接口也不必提前细分成几十个小接口。应从真实变化出发：稳定、普遍存在的能力放在核心接口，只有出现明确分歧时才拆分。抽象的收益，体现在下一次接入时能够少改哪些代码，而不在于今天画出了多少层类图。

验证这套设计时，可以用同一组契约用例检查所有实现：正常轨迹、查无结果、鉴权失败、字段缺失。再增加甲乙并发查询的用例，确认请求身份不会串用。最终得到的是一条清晰的扩展路径：配置承接接入差异，策略承接协议差异，主流程继续围绕统一能力工作。
