# 模板方法实战：统一任务生命周期，保留渠道步骤的控制权

一个导出服务同时生成 CSV、Excel 和 PDF。三种任务都要校验参数、加载数据、生成文件、保存结果、记录耗时，但文件生成过程完全不同。最直接的实现是复制三份完整流程，分别改中间一段。需求少时这样很快，随后增加取消、错误分类或审计字段，就要在三处同步修改。

模板方法适合处理这类“执行骨架稳定、某些步骤变化”的场景。它把顺序固定下来，让具体实现只承担确实不同的部分。

## 先找稳定顺序，再设计扩展点

导出任务可以分成以下生命周期：

![导出任务的公共生命周期与格式差异步骤](博客公开附件/工程实践/模板方法实战-统一任务生命周期，保留渠道步骤的控制权.png)

其中，参数是否满足格式要求、怎样把数据渲染为文件，适合留给具体格式。任务编号、时间记录、结果状态和临时目录清理，则应保持一致。

```java
abstract class ExportTask {
    public final ExportResult execute(ExportContext ctx) {
        long started = System.nanoTime();
        try (Workspace workspace = Workspace.create(ctx.jobId())) {
            validate(ctx);
            DataSet data = loadData(ctx);
            Path file = render(ctx, data, workspace);
            StoredFile stored = publish(ctx, file);
            return ExportResult.success(ctx.jobId(), stored);
        } catch (ExportException e) {
            return ExportResult.failed(ctx.jobId(), e.code());
        } finally {
            recordDuration(ctx.jobId(), System.nanoTime() - started);
        }
    }

    protected abstract void validate(ExportContext ctx);
    protected abstract Path render(ExportContext ctx,
                                   DataSet data, Workspace workspace);
    // loadData、publish、recordDuration 为公共步骤
}
```

这里的 `final` 表达一项设计约束：格式实现可以改变某一步的算法，不能偷偷绕过整个生命周期。代码是结构示例，具体存储、取消和异常映射仍由组件契约决定。

## 扩展点应围绕职责，而不是每一行代码

把每个小动作都变成 `beforeX()`、`afterX()`，会让子类通过任意钩子改变流程。阅读者必须在父类和多个子类之间来回跳转，才能判断究竟执行了什么。

更有效的扩展点具有明确输入、输出和副作用边界。例如 `render()` 接收已经确定的数据集，输出临时文件；它不更新任务终态，也不向用户发送完成通知。PDF 实现可以分页，Excel 实现可以拆工作表，但都不能另起一套成功通知逻辑。

| 步骤 | 公共层负责 | 格式实现负责 |
|---|---|---|
| 参数检查 | 必填字段、任务身份 | 工作表上限、页面尺寸 |
| 数据准备 | 统一查询范围 | 必要的格式化映射 |
| 生成文件 | 临时目录生命周期 | 编码、分页、单元格布局 |
| 发布结果 | 文件引用、最终状态 | 提供有效产物 |

这张职责表也能减少接口膨胀。如果一个差异只影响一个算法，就把它保留在算法内部，不必提升为所有子类都要理解的新钩子。

## 公共异常处理不等于公共重试

捕获异常、记录耗时可以集中处理；“异常后从头再跑”则需要更谨慎的语义。读取数据失败通常没有副作用，重新读取较容易；文件已经上传成功但响应丢失时，再次上传可能生成第二份对象。

因此，模板可以统一输出 `FAILED`、`CANCELED` 等结果，却不应把所有异常都解释成“允许重试整个任务”。重试策略应知道失败阶段，并由该阶段说明操作是否可重入。发布文件时使用稳定对象键，或先确认已存在的文件，可以把重复尝试收敛到同一产物。

同样，`finally` 适合清理本地临时目录，因为目录明确属于本次执行；它不适合无条件撤销远端结果。清理资源和补偿业务是两个不同职责。

## 当变化开始改变顺序时

如果 CSV、Excel 只是生成方式不同，继承模板很自然。若一种导出必须先请求授权、异步等待外部处理、再分页下载，另一种只需本地计算，强行共用一条长模板就会出现大量分支和空钩子。

此时可以保留任务状态、日志、存储等公共组件，让不同流程通过组合编排。策略模式负责选择实现，模板方法负责约束稳定顺序，组件组合负责承接结构差异，三者可以同时存在。

评估模板设计的一个好方法，是新增第四种格式：它是否只需要实现明确的差异步骤？公共层增加耗时字段后，所有格式是否自然获得一致记录？这些变化是否保持局部，比“消除了多少行重复代码”更能说明抽象是否合适。
