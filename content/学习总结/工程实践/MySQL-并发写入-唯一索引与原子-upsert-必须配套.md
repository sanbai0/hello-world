# MySQL 并发写入：唯一索引与原子 upsert 必须配套

两个消息同时到达，都要更新会话 C-42 的最后活跃时间。会话第一次出现时数据库里还没有记录，于是代码采用“先更新，更新不到再插入”。单线程测试很顺利，线上并发后却出现两条相同会话。

问题不在 `UPDATE` 失效，而在两个独立请求都能合法地走到“没有记录，准备插入”的分支。

## 把竞态展开到时间线上

```text
请求 A：UPDATE C-42 → 影响 0 行
请求 B：UPDATE C-42 → 影响 0 行
请求 A：INSERT C-42 → 成功
请求 B：INSERT C-42 → 成功
```

如果数据库没有约束 C-42 只能存在一条，这四步完全合法。应用层的“先查询是否存在”也一样：查询与插入之间仍有空隙。给单进程加锁只能协调当前实例，多实例和后台补数脚本仍可能同时写入。

首先应该回答数据模型问题：什么字段组合定义了“一条会话”？

## 唯一索引表达的是业务身份

假设会话编号只在租户内部唯一，那么唯一键应是 `(tenant_id, conversation_id)`，而不是单独的 `conversation_id`。

```sql
CREATE TABLE conversation (
    id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    conversation_id VARCHAR(64) NOT NULL,
    last_message_at DATETIME(6) NOT NULL,
    UNIQUE KEY uk_tenant_conversation
        (tenant_id, conversation_id)
);
```

内部主键提供稳定引用，业务唯一键阻止重复身份。两者可以同时存在。唯一索引还让所有写入入口遵守同一项约束，包括接口、消费者、导入脚本和管理工具。

当历史表已经有重复记录时，不能直接假设加索引就会成功。需要先明确保留哪条主记录、如何合并字段，以及其他表的引用如何处理。最后在控制并发写入的迁移窗口中建立约束，避免刚清理完又产生新重复。

## 用一条语句处理创建与更新

有了唯一键，MySQL 的 upsert 才知道应该把哪一种冲突转为更新。以下语句展示命名参数风格，实际占位符由数据库驱动提供：

```sql
INSERT INTO conversation
    (tenant_id, conversation_id, last_message_at)
VALUES
    (:tenant_id, :conversation_id, :message_time)
ON DUPLICATE KEY UPDATE
    last_message_at = GREATEST(last_message_at, :message_time);
```

并发插入同一个业务身份时，唯一约束负责裁决，语句按冲突路径更新已有记录。调用方不再先做一次“是否存在”的猜测。

这里使用 `GREATEST` 还有一个独立目的：消息可能乱序到达。10:05 的消息先写入，10:03 的旧消息随后补到时，最后活跃时间仍应保持 10:05，而不是被旧时间覆盖。

这说明 upsert 不只是减少 SQL 数量。冲突后每个字段如何合并，仍需要按照业务含义设计。

| 字段类型 | 示例合并策略 |
|---|---|
| 首次出现时间 | 保留较早时间 |
| 最后活跃时间 | 保留较晚时间 |
| 不可变业务身份 | 不在冲突路径覆盖 |
| 最新内容 | 按可靠版本或事件顺序判断 |
| 累计计数 | 先确认事件是否首次应用 |

## 行唯一，不等于事件只处理一次

如果每收到一条消息就执行 `message_count = message_count + 1`，同一消息重投两次仍会加两次。唯一会话行只保证“一条会话只有一行”，不保证“同一消息只影响一次”。

对于需要精确累计的场景，可以在同一数据库事务中先写入带唯一事件编号的接收记录，只有首次插入成功才更新计数；重复事件直接复用处理结果。去重身份还应包含必要的租户或来源范围，避免不同来源恰好使用相同编号。

如果当前字段只是取最大时间，重复执行天然不会改变最终值，就不一定需要额外计数去重。这类合并规则既简单，也更适合处理重投和乱序。

## 用并发结果检查设计

让多个并发请求同时写入 C-42，最终应只有一行；让较旧消息晚到，最后活跃时间应保持最新；让同一事件重复到达，具有累计语义的字段不应重复增加。

三项检查分别对应身份约束、字段合并和事件幂等。把它们分开，便能避免把所有并发问题都归结为“换成 upsert 就好了”。在这个例子里，唯一索引确定会话身份，upsert 收拢创建与更新，时间合并规则处理乱序，数据库最终保存的含义才与业务一致。[MySQL upsert 官方说明](https://dev.mysql.com/doc/refman/8.0/en/insert-on-duplicate.html)
