# 业务后台故障，聊天还能继续：MQTT + Redis 的聊天架构设计

聊天系统的功能会越来越多，但用户最直接的要求始终很简单：消息能发出去，对方能收到。

在客服场景里，接待统计、聊天记录查询、业务信息联动和 AI 回复都围绕对话展开。这些能力可以持续迭代，基础通讯却需要保持稳定。业务后台正在发布，或者某个统计接口出了问题，不应该轻易打断用户与客服正在进行的沟通。

围绕这个需求，我们采用的设计思路是：用 MQTT 承担实时通讯，用 Redis 管理会话绑定，将统计、日志分析和 AI 回复作为独立能力接入。让基础聊天拥有自己的运行路径，是这套架构的核心目标。

## 从业务后台集中处理聊天说起

一种常见的起步方式，是把聊天作为业务后台中的一个模块。客户端通过 HTTP 接口提交消息，后台完成身份校验、会话查询、消息存储，再通过 WebSocket、长轮询等方式把消息推送给接收方。

```text
用户发送消息
    ↓
HTTP 聊天接口
    ↓
业务后台：鉴权 → 查询会话 → 保存消息 → 调用相关业务
    ↓
消息推送
    ↓
客服收到消息
```

这种方式有实际优势：用户、权限、会话和业务数据集中在一起，开发人员容易理解调用过程，也方便在同一套代码里实现功能。项目初期，直接复用已有后台通常能更快交付。

这里讨论的是“以业务后台为中心的消息处理方式”。HTTP 本身并不妨碍系统扩展，WebSocket 也不会自动消除业务耦合；真正需要关注的是，一条消息到达接收方之前，必须等待哪些服务完成。

## 功能增长后，聊天开始承担过多依赖

随着需求增加，一条聊天消息可能还要触发接待统计、业务日志、搜索索引更新和 AI 判断。如果这些处理逐渐进入同步发送流程，消息延迟就会受到越来越多环节的影响。

例如，客服只想发送一句“正在为您处理”，却需要等待一个耗时的业务查询。或者统计任务与聊天接口共享进程和数据库连接池，统计流量上升后，普通消息也开始排队。

集中在同一个后台，还意味着发布与故障范围容易扩大：修改一个报表功能，需要发布承载聊天接口的服务；后台异常重启，正在使用聊天的用户也可能受到影响。即使改成异步调用，如果大家仍争用同一批资源，隔离效果也有限。

公司的客服场景需要同时满足几件事：用户与客服持续沟通，接待关系能够分配和转接，统计与记录能够独立处理，AI 可以逐步接入。这里面，基础收发与扩展业务的变化频率、耗时和可用性要求并不相同。

因此，架构上的目标变得明确：**把实时通讯从业务后台的日常处理链路中分离出来，让扩展功能围绕聊天工作，避免每条消息都等待整套业务系统。**

## 让 MQTT 通讯与 Redis 绑定各司其职

新的结构可以分为通讯、会话管理和扩展服务三个部分。

```text
会话建立：客户端 → 认证 / 分配服务 → Redis 会话绑定
                         ↓
                  会话信息与访问授权

基础聊天：用户端 ←→ MQTT Broker ←→ 客服端
                         │
                         └→ 异步事件通道
                               ├→ 记录归档 / 日志分析
                               ├→ 接待统计
                               └→ AI 服务 → 受限发布身份 → Broker
```

MQTT Broker 负责连接、订阅与消息分发；Redis 保存谁正在与谁沟通、当前接待客服是谁等绑定关系；业务服务负责登录、分配、转接和其他管理操作。

这里所说的客户端直接通讯，是双方通过 Broker 交换消息，无需让业务后台逐条转发。它仍然需要通讯服务中转，不是设备之间的 P2P 连接，也不自动具备端到端加密。MQTT 的发布订阅模型见 [OASIS MQTT 规范](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)。

### 从一次访客接入看运行过程

访客进入客服页面后，先完成身份认证。分配服务查询 Redis：如果已有有效会话，就复用原接待关系；如果没有，再分配客服并建立绑定。

一份简化的绑定可以表示为：

```text
会话编号：S-42
访客编号：U-17
客服编号：A-08
绑定版本：3
会话状态：进行中
```

服务随后下发会话信息和有限的访问授权。双方连接 Broker，订阅自己有权接收的消息主题。访客发布消息后，Broker 根据订阅与权限完成投递；客服回复走同样的路径。

绑定建立之后，正常消息不必每次都调用业务接口重新查询接待对象。这既减少了网络往返，也缩小了业务后台波动对实时聊天的影响。

需要转接时，再由会话管理服务协调绑定更新、旧权限撤销和新权限授予。Redis 承担关系状态，Broker 执行实际通讯权限，两边必须有一致的版本和切换流程，不能只改一条绑定就认为转接完成。

### 统计、日志和 AI 如何接入

消息产生后，扩展服务通过订阅或异步事件通道获得事件。统计服务累计接待情况，归档服务处理记录，AI 服务按规则读取用户输入并生成回复。

人工消息到达对方，不需要等待报表计算或者模型推理结束。AI 服务升级时可以单独暂停，统计服务积压时可以独立扩容；新增一种分析能力，也不必重新编排每条聊天消息的发送流程。

这种外接方式需要真正异步。如果 Broker 收到消息后同步请求业务接口，并等待结果才转发，依赖关系实际上又回到了原点。旁路消费者也需要独立配额和有界缓冲，避免一个处理很慢的服务耗尽通讯层资源。

## 独立运行带来的价值

最直接的收益是故障影响范围变得清楚。在连接、订阅与授权仍有效，且通讯基础设施正常的前提下，业务管理后台暂时不可用，已有会话仍可以继续收发消息。

| 出现问题的部分 | 可以保留的能力           | 暂时受影响的能力                   |
| -------------- | ------------------------ | ---------------------------------- |
| 接待统计       | 用户与客服继续沟通       | 统计结果延迟更新                   |
| AI 服务        | 人工消息继续收发         | 自动回复暂停                       |
| 业务管理后台   | 已建立的有效会话继续聊天 | 新建会话、转接等管理动作可能不可用 |
| 历史查询服务   | 实时消息继续投递         | 查看历史记录受影响                 |

第二个收益是可以按负载扩容。在线连接与消息投递增加时，扩展通讯层；统计处理不过来时，增加消费者；AI 推理需要更多资源时，单独调整 AI 服务。不同能力不必绑定在同一组业务实例上增长。

这也使系统更适合承接大流量：基础链路只承担必要的通讯工作，耗时业务通过异步通道处理。但“连接数很多”与“消息吞吐很高”是两个不同指标，实际容量仍取决于消息大小、接收终端数量、权限检查、持久化和部署资源，不能仅由技术组件名称推导。

第三个收益是降低日常迭代对聊天的扰动。统计口径、AI 策略和业务管理功能可以持续变化，通讯层围绕较稳定的职责演进。业务后台维护时保住正在进行的对话，比单纯把服务数量拆多更有意义。

## 要把这套设计落地，还需要解决什么

独立运行需要一套完整的通讯边界。以下问题应该由对应层承担，而不是在故障发生后临时补救。

### 鉴权：让通讯层能够独立做出授权判断

客户端只能发布和订阅自己有权限的主题。主题名里带了用户编号，并不代表别人无法猜到，更不能把客户端提交的发送者字段直接当作可信身份。

一种可行方式是由认证服务签发有时限的凭证，通讯层独立验证签名，并结合会话权限控制访问。身份来自可信连接，发布权限精确到允许的主题；转接、封禁和退出则有独立的权限撤销机制。

需要明确的是，凭证到期和断线重连可能重新依赖认证服务。保持已有会话运行，与后台故障期间仍能完成所有新登录，是不同的可用性目标。不能为了“不断线”而无限延长旧权限。

### 消息可靠性：明确“发送成功”承诺了什么

客户端提交、Broker 接收、对端收到和用户已读，是不同的状态。MQTT 的协议确认不能直接代表用户已经看到消息，QoS 1 也允许重复投递；应用层需要稳定的消息 ID、去重和收件回执。[MQTT QoS 说明](https://docs.oasis-open.org/mqtt/mqtt/v5.0/mqtt-v5.0.html)

如果要求服务确认后，即使接收方离线或节点重启，消息仍然可以恢复，就需要可靠的持久接收机制。可以由支持相应能力的 Broker 或独立消息存储层承担，再把分析、检索和报表放到旁路。

因此，“记录外接”要区分两件事：历史查询与分析可以独立，唯一一份可靠消息副本不能只是随时可能丢失的异步日志。持久化不可用时，必须按既定策略排队、拒绝或明确降级，不能一边丢失记录，一边继续显示可靠发送成功。

### 重连与绑定：恢复旧会话，避免重复分配

网络抖动后，客户端应按退避策略重连，恢复订阅，并根据消息游标补拉缺失记录。实时收到的消息与补拉结果，通过消息 ID 合并去重。

重新进入页面时，应优先复用有效绑定，避免访客因一次刷新就换了客服。转接使用绑定版本防止旧事件覆盖新状态；结束会话则需要同时处理关系回收和权限撤销。

Redis 的过期时间适合清理临时状态，但键过期不等于完整的会话结束流程。心跳、业务会话和授权各自的生命周期需要分开设计，具体过期行为见 [Redis EXPIRE 文档](https://redis.io/docs/latest/commands/expire/)。

### 旁路故障：积压可控，恢复时不重复执行

统计和归档消费者需要按消息 ID 幂等处理，防止重试造成重复记录或重复计数。积压要有容量上限、告警与恢复策略，不能依靠无限增加内存维持“异步”。

AI 在发出回复前，还应检查当前会话、人工接管状态与回复时效。延迟很久才生成的答案，不应自动发到已经结束或转接的对话里；AI 自己产生的消息，也不能再次触发同一套自动回复循环。

这些设计会增加部署和维护成本。Broker、Redis、消息存储及消费者都有各自的状态，排障时需要统一的消息标识和链路记录。对于规模很小、功能稳定的系统，集中式实现可能更经济；当基础通讯需要长期稳定、外围功能持续增长时，这种拆分的收益才更明显。

## 用故障场景验证“聊天还能继续”

验收不能只看 Broker 进程是否存活。应先建立一对真实会话，再在测试环境分别停止业务后台、统计与 AI 服务，检查双方是否仍能持续收发，以及延迟和消息状态是否符合预期。

然后单独验证断线重连、凭证到期、转接和旁路积压。这样可以明确：哪些故障只影响扩展功能，哪些会影响新会话，哪些属于通讯基础设施本身的问题。本文讨论的是架构与验收思路，不把未经测量的吞吐量或故障结果写成已经实现的保证。

这套设计最终希望建立一个稳定的分工：基础通讯保证消息在授权范围内可靠流转，Redis 与会话服务管理接待关系，业务能力通过事件逐步扩展。即使业务后台暂时出现问题，用户与客服之间已经建立的沟通，也仍有一条能够继续运行的路径。
