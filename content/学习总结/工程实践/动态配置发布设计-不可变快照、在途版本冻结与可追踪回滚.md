# 动态配置发布设计：不可变快照、在途版本冻结与可追踪回滚

一个订单任务入队时，运费规则是“满 100 元包邮”；等待执行期间，运营把门槛改成 150 元。任务计算出费用后重试，发送前又读取了最新配置。

每个组件都在积极使用“最新规则”，同一笔订单却可能在不同步骤得到不同解释。异步系统中的配置，除了当前值，还需要一个稳定的版本身份。

## 把内容与生效指针分开

规则内容保存为不可变快照，发布记录负责决定哪份快照对新任务生效：

```text
rule_snapshot
  id, schema_version, content, content_hash

release_state
  active_snapshot_id, previous_snapshot_id, generation

job
  id, rule_snapshot_id, status
```

编辑产生草稿，校验通过后生成新快照；发布只切换指针，不原地修改历史快照。这样草稿可以多次保存，线上仍继续使用上一份已发布内容。

`schema_version` 描述数据结构，快照 ID 描述具体内容，`generation` 描述第几次发布。三者职责不同：同一种结构可以发布很多内容；回滚到旧内容，也应该产生一次新的发布操作。

## 任务从入口带着版本走

假设任务 A 入队时绑定快照 7，之后发布快照 8，任务 B 才进入系统：

| 动作 | 任务 A | 任务 B |
| --- | --- | --- |
| 入队绑定 | 版本 7 | 版本 8 |
| 第一次执行 | 版本 7 | 版本 8 |
| 失败后重试 | 版本 7 | 版本 8 |
| 结果发送前复核 | 版本 7 | 版本 8 |

版本 ID 与任务一起持久化。执行、重试和发送阶段按该 ID 读取内容，不再重新询问“现在最新的是哪一版”。发布与任务入队并发时，以入口读取到的已提交指针作为绑定依据，并把它保存到任务记录。

这使一项任务拥有可解释的统一规则，即使进程重启，也能复原当时的判断条件。历史快照因此需要引用保留策略：仍被在途任务或必要审计记录引用的内容，不能随意删除。

## 并发发布用条件更新保护

两位编辑者同时从发布序号 20 开始修改。第一位已经发布，序号变为 21；第二位仍按旧草稿直接覆盖，就可能无意抹掉第一位的变更。

发布请求可以携带 `base_generation`，在事务内执行条件更新：

```sql
UPDATE release_state
SET previous_snapshot_id = active_snapshot_id,
    active_snapshot_id = :new_id,
    generation = generation + 1
WHERE singleton_id = 1
  AND generation = :base_generation;
```

更新 1 行才表示发布成功；更新 0 行说明基线已变化，应让编辑者重新比较。发布指针、审计记录与必要状态在同一事务中提交，避免出现配置已生效却找不到发布人的情况。

条件更新保护的是发布并发，不替代内容校验。快照生成前仍需校验必填字段、重复规则、优先级冲突，以及代表性输入的预期输出。

## 回滚是一次新发布

从快照 8 回到快照 7，可以将活动指针切回 7，同时让发布序号继续递增，并记录原因。审计链表达的是“发布过 8，随后撤回”，而不是假装 8 从未出现。

已经绑定快照 8 的任务通常继续按 8 执行；若规则涉及必须立即停止的风险，需要另设任务取消或执行门禁，明确处理这些任务。静默替换它们的版本会破坏重试一致性，也让结果失去解释依据。

缓存可以按快照 ID 和内容摘要保存不可变对象，既减少反复加载，又不会把当前指针藏在过期缓存里。对缓存对象进行防修改处理，防止一次调用改动共享结构，污染同版本的后续任务。

## 用跨版本任务验证契约

一组小而完整的验证过程是：入队 A，发布新版本，入队 B，重启执行器，再让 A、B 分别重试。检查两项任务是否始终使用自己的版本。随后回滚，新增 C，确认 C 使用回滚后的内容，而 A、B 的引用不变。

快照缺失或摘要不符时，也不能偷偷读最新版本。对于已绑定任务，应停止相关动作并报告具体版本；这样错误会被暴露在正确的位置，而不会生成一份看似成功却无法复现的结果。

动态配置的成熟度，体现在变更影响范围是否明确。内容不可变、任务有版本、发布有顺序、回滚有记录，才能让灵活更新与执行一致性同时成立。
