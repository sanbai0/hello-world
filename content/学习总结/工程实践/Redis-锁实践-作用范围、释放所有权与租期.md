# Redis 锁实践：作用范围、释放所有权与租期

多个实例共享一个外部账号，而外部平台只允许这个账号同时执行一项操作。常见做法是用 Redis 锁串行化任务：获取锁，调用接口，最后释放。代码只有几行，但互斥是否成立，取决于锁保护的资源、持有者身份以及有效时间。

尤其值得检查的，是释放路径。`finally` 能保证清理发生，却不能保证执行清理的人仍然拥有这把锁。

## 锁键先对应真正共享的资源

如果限制是“同一个外部账号只能运行一个任务”，锁键就应围绕外部账号构造，而不是围绕本次任务 ID。两个任务使用不同任务锁，对共享账号没有互斥效果。

反过来，把所有账号放进一把全局锁，虽然限制了并发，也会把本可独立执行的任务串行化。锁的粒度应与资源冲突范围一致，例如：

```text
lock:external-operation:{platform}:{account-id}
```

所有执行入口还需要使用同一个 Redis 逻辑空间与键规则。后台定时任务和 HTTP 接口各自维护一把本地锁，不能形成跨实例保护。

## 未获得锁的任务，没有释放资格

以下时序说明了直接 `DEL` 的风险：

| 时刻 | 任务 A | 任务 B | 任务 C |
| --- | --- | --- | --- |
| t1 | 获得锁，开始执行 | — | — |
| t2 | 仍在执行 | 获取锁失败 | — |
| t3 | 仍在执行 | `finally` 无条件删除锁 | — |
| t4 | 仍在执行 | 已结束 | 获得锁，开始执行 |

此时 A 与 C 同时操作同一账号。B 的本意只是清理，却删除了属于 A 的共享状态。

至少要把清理范围收敛到“成功获得锁之后”。但仅记录一个本地布尔值仍然不够，因为锁可能在执行期间过期，随后被其他任务重新获得。

## 每次获取都带独立 token

获取锁时，为这次持有关系生成独立、足够随机的 token，并把 token 与租期一起设置：

```text
SET lock-key unique-token NX PX 30000
```

只有命令成功才进入受保护区域。释放时，Redis 中的值必须仍等于本次 token，才允许删除：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

比较与删除需要在同一个原子操作中完成。应用侧先 `GET` 再 `DEL`，两次命令之间仍可能发生过期和重新获取。Lua 脚本避免了“检查时是自己的，删除时已经属于别人”的间隙。

token 表达的是一次获取关系，不只是某台机器的身份。同一实例连续执行两个任务，也应生成两个 token，防止上一轮迟到的清理影响下一轮。

## 安全释放与租期，是两个约束

假设 A 获得三十秒租期，接口调用却用了四十五秒。第三十秒后 B 可以获得锁，A 此时仍可能继续运行。token 校验能够阻止 A 结束时误删 B 的锁，却无法让已经发生的并行操作消失。

租期策略应与任务性质配套：耗时有可靠上界的任务，可以设置覆盖执行与清理的期限；长任务可以按持有者身份续租，并在失去所有权后停止发起新的受保护动作。续租同样需要原子校验 token，不能为别人的锁延长租期。

进程暂停或网络分区会让续租失败，因此“自动续租”也不能代替下游约束。对能控制的存储服务，可以使用单调递增的 fencing token，让资源端拒绝旧持有者的写入。普通第三方 HTTP 接口如果没有这种能力，就无法凭空获得这一保证，应结合接口幂等键、任务期限和结果确认设计流程。

## 用竞争时序检验，而不只测加解锁

最有价值的验证是人为制造边界：B 获取失败后执行清理，A 的锁应仍存在；A 的锁过期并由 B 获得后，A 再释放应返回未删除；续租失败后，执行者不能继续开启新的外部动作。

任务日志可以记录资源标识、持有 token 的摘要、获取结果、租期与释放结果。这样能够区分“没有获得锁”“已经失去所有权”和“正常释放”，而不是把所有失败都写成同一个异常。

Redis 锁的可靠用法并不止于一个加锁 API。资源范围决定谁需要互斥，token 决定谁有权清理，租期决定这项权利持续多久。三者与真实执行流程对应起来，锁才能成为并发协议的一部分。
