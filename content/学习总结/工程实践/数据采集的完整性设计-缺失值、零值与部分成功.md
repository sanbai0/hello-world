# 数据采集的完整性设计：缺失值、零值与部分成功

一个采集接口声明列表共有 498 件商品，运行到第 400 件时登录失效。程序把已经取得的数据保存成 JSON，文件可以读取，字段结构也正常。此时该怎样交付：算成功，算失败，还是全部丢弃？

答案取决于下游准备拿这份数据做什么。用来展示已有条目，可以继续使用；用来判断哪些商品已经下架，就不能把没抓到的 98 件当成不存在。采集结果除了数值，还需要表达覆盖范围和完整性。

## 一次任务至少有两种覆盖率

列表是否收全，与字段是否读全，是两个维度。假设已取得的 400 件商品全部检查了定金字段，其中 380 件具有可解释的金额，20 件缺少该字段：

| 指标 | 数值 | 能说明什么 |
| --- | ---: | --- |
| 预期商品数 | 498 | 当前声明的采集范围 |
| 去重后已取得商品数 | 400 | 已掌握哪些商品 |
| 已检查定金的商品数 | 400 | 已返回商品均经过字段检查 |
| 定金值已知的商品数 | 380 | 有多少商品具有确定金额 |
| 定金值未知的商品数 | 20 | 哪些商品还缺少证据 |

检查率达到百分之百，不意味着值已知率也是百分之百；已返回商品全部检查过，也不意味着整份列表已经收齐。把这几个概念分开，下游才能判断可用程度。

## 零值是事实，空值是未知

如果平台明确返回定金为零，保存 `0` 是正确的。如果字段缺失、解析失败或尚未读取，应保留 `null`，并记录原因。

```json
{
  "product_id": "product-demo-17",
  "deposit_cents": null,
  "deposit_status": "missing",
  "source": "list_response"
}
```

为了表格整齐而把未知写成零，会永久丢失原始信息。后续看到一个零，已经无法判断它是平台明确表示无需定金，还是采集器没有读到。

计算层可以有自己的假设，例如在粗略估算时把未知定金暂按零计算，但结果必须携带该假设。原始事实与计算假设分开保存，重新获得数据后才能准确重算，而不是先猜一个值，再把猜测当成平台数据。

## 部分快照应该拥有更少的更新权限

完整性不是日志里的提示文案，而是同步操作的约束。处理部分快照时，可以更新这 400 件已经确认的商品；不能因为其他旧商品本次没出现，就把它们删除、下架或金额清零。

![采集完整性决定同步权限](博客公开附件/工程实践/数据采集的完整性设计-缺失值、零值与部分成功.png)

```python
for item in snapshot.items:
    upsert_observed_fields(item)

if snapshot.complete:
    reconcile_missing_items(snapshot.scope, snapshot.observed_ids)
```

这段伪代码还有一个含义：更新已观察字段，而不是用整条记录的默认值覆盖所有旧字段。某商品这次拿到价格却没拿到定金，可以更新价格并保留定金未知的本次观察状态，是否继续展示旧值则由明确的数据新鲜度规则决定。

完整快照也不自动授权跨范围处理。只采集“某个活动中的在售商品”，缺席状态最多适用于同一活动、同一筛选条件，不能据此删除商品主数据。

## “完整”本身也要有判定依据

只比较条数并不充分。抓到 498 行可能包含重复 ID，也可能分页期间列表发生增删。可靠的采集元数据应记录查询范围、去重数量、分页终止依据以及必要的批次或快照标识。

```json
{
  "scope": {"event_id": "event-demo", "filter": "on_sale"},
  "complete": false,
  "expected_count": 498,
  "observed_count": 400,
  "failure_reason": "session_expired",
  "result_available": true
}
```

若来源提供稳定快照令牌，整次分页应沿用同一个令牌。如果来源只能提供实时列表，就要据其契约判断能否声明完整；不能仅凭首页总数与最后行数相同，推断拥有强一致快照。

## 把验收落在下游动作上

一组有价值的验收样例，应包括完整列表、途中中断、重复商品、缺失字段和显式零值。检查的不只是输出 JSON，还包括数据库更新之后，未返回的旧商品有没有被错误移除，未知金额有没有变成零。

上面的 400 件示例中，正确结果是保留可用数据、明确标记部分完成，并禁止根据缺席执行清理。重新采集得到完整快照后，再按照相同范围进行完整同步。

这样设计之后，失败不再只有“全部成功”与“全部作废”两个选项。每批数据都携带足够的解释，使下游能够安全使用已经确认的部分，同时等待尚未确认的部分。
