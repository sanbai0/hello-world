# 有限资源分配：从逐项排名到两层动态规划

一家小型仓库准备把两份包装材料分配给三个订单。给订单 A 两份，能节省 15 元运费；给 B 一份，节省 9 元；给 C 一份，节省 8 元。按单个订单的节省金额排名，A 排第一；真正最划算的组合却是 B+C，总共节省 17 元。

| 订单 | 可选方案 | 消耗材料 | 节省金额 |
| --- | --- | ---: | ---: |
| A | 普通包装 / 合并包装 | 0 / 2 | 0 / 15 |
| B | 普通包装 / 优化包装 | 0 / 1 | 0 / 9 |
| C | 普通包装 / 优化包装 | 0 / 1 | 0 / 8 |

每个订单单独计算都没有错，错误来自把“单项最好”直接当成“组合最好”。共享库存、执行名额、预算额度，都容易遇到同一种问题：选择一项方案，会改变其他方案是否还能被选择。

## 先把复杂规则关进局部方案表

如果包装方式还受到商品数量、包裹重量、每箱容量影响，直接写一个遍历全部订单和全部组合的大循环，会让业务规则与资源分配纠缠在一起。

更清晰的做法是分两层。局部层负责一个订单内部的组合，例如拆成几个包裹、使用什么包装、每种材料各需要多少；全局层只接收局部层生成的候选方案，决定各订单选哪一个。

局部方案可以表示为：

```text
方案 = {资源用量向量, 收益, 执行明细}
例如：{[1, 2], 1800分, [小箱1个, 缓冲包2个]}
```

向量中的位置要固定：第一项始终是纸箱，第二项始终是缓冲包。不同资源不能因为都叫“数量”就加成一个总数。局部层还要保留不使用稀缺资源的方案，否则全局层会被迫给每个订单分配材料。

有些候选可以提前去掉：同一订单中，如果方案 X 消耗各类资源都不少于 Y，收益又不高于 Y，并且没有额外的执行优势，X 就被 Y 支配。删除这种候选能缩小搜索量，同时保留原问题的最优结果。

## 全局层是“每组只能选一个”的动态规划

把每个订单看成一组候选方案。设 `dp[r]` 表示处理完前几组、恰好使用 `r` 份材料时，能够达到的最大收益。初始只有 `dp[0] = 0`，其他状态不可达。

下面的伪代码只展示一类资源，多类资源时把 `r` 换成资源向量：

```python
dp = {0: 0}
for plans in order_groups:
    next_dp = {}
    for used, value in dp.items():
        for plan in plans:  # 包括不使用材料的方案
            new_used = used + plan.cost
            if new_used <= capacity:
                candidate = value + plan.gain
                next_dp[new_used] = max(
                    next_dp.get(new_used, float('-inf')),
                    candidate,
                )
    dp = next_dp
```

这里每一组都从旧 `dp` 生成新 `next_dp`，是一个重要细节。如果边读边改同一张表，后面的转移可能再次使用本组刚产生的结果，相当于给同一个订单选择多个互斥方案。

开头的例子可以手算出每层结果，破折号表示不可达：

| 处理进度 | 使用 0 份 | 使用 1 份 | 使用 2 份 |
| --- | ---: | ---: | ---: |
| 初始 | 0 | — | — |
| 加入 A | 0 | — | 15 |
| 加入 B | 0 | 9 | 15 |
| 加入 C | 0 | 9 | **17** |

最后从所有不超过容量的状态中取最大值，而不是只读取“库存恰好用完”的状态。资源用不完可能正是合理答案。

## 把答案还原成可执行方案

只返回 17 元，还不足以交付一个规划工具。每次更新最优值时，还应记录上一层状态与本次选中的方案，最终从最佳状态沿父节点回溯，得到 B 和 C 的选择。

回溯记录需要属于对应层，不能被后续更新覆盖。可以保存不可变的链式节点，避免每次状态转移都复制完整方案。收益相同时，再约定固定规则，例如优先少用资源，仍相同时按稳定的方案编号选择，保证重复计算能得到可解释的结果。

多维状态空间大致随各类库存的乘积增长。上线前可以按业务上限做无损裁剪，例如最多执行十个订单，每单最多用一个纸箱，就无需考虑一万只纸箱的库存状态；超过计算预算时，也可以明确返回规模过大，或提供标注为近似的结果。

两层设计的价值在于分工清楚：局部层证明某个订单怎样执行，全局层证明共享资源没有超用。规则增加时有明确修改位置，结果异常时也能沿着方案表与回溯路径定位，而不必在一个巨大搜索过程里猜测。
