# UPDATE 误更新：唯一标识、状态条件与影响行数

一条 `UPDATE` 能执行成功，只说明数据库接受了这条语句；它是否只修改了目标记录，还取决于 `WHERE` 能否准确表达“正在操作哪一个对象”。

以库存预留为例：仓库 A 和仓库 B 都有货品编码 `SKU-42`，每次预留会生成一条记录。订单取消时，需要释放某一条预留。下面这条 SQL 很短，也很危险：

```sql
UPDATE stock_reservation
SET status = 'RELEASED'
WHERE sku_code = 'SKU-42';
```

货品编码描述“是什么货”，预留记录描述“哪一次占用”。二者不是同一种身份。即使补上仓库编号，同一仓库也可能同时存在多笔预留，条件仍然不足以定位一次操作。

## 用一张小表检查条件覆盖面

| id | warehouse\_id | sku\_code | order\_id | status |
|---:|---|---|---|---|
| 101 | A | SKU-42 | O-11 | RESERVED |
| 102 | A | SKU-42 | O-12 | RESERVED |
| 103 | B | SKU-42 | O-13 | RESERVED |

假设要释放订单 O-11 的预留，目标集合应该只有第 101 行。逐个检查 SQL 条件，就能直观看到它匹配了几行。这比先讨论要不要加锁更有效：锁能协调并发，却不能修正一个匹配错对象的条件。

较稳妥的做法，是在创建预留时就保存内部主键，后续状态变更始终使用这个身份。外部编码适合查询和展示，内部主键负责精确寻址；两者之间的映射应在进入更新步骤前确定。

## 对象正确，还要状态正确

只按主键更新，可以保证不会改到其他记录，但仍可能把已经发货的记录改成“已释放”。状态条件负责约束允许发生的转换：

```sql
UPDATE stock_reservation
SET status = 'RELEASED',
    version = version + 1
WHERE id = :reservation_id
  AND tenant_id = :tenant_id
  AND status = 'RESERVED';
```

`id` 回答改谁，租户条件约束操作范围，`status` 回答从什么状态出发。版本号在这里用于记录变化；如果调用方还需要防止基于旧内容更新，可以额外加入 `AND version = :expected_version`。

带预期状态的单条更新，可以把“检查仍可释放”和“执行释放”交给数据库一起完成。若先 `SELECT` 再无条件 `UPDATE`，两个语句之间仍可能插入另一个请求，把记录推进到新的状态。

## 影响行数是业务结果的一部分

DAO 返回值不能在服务层被随手丢弃。对于“从 RESERVED 变为 RELEASED”的更新，成功路径应影响一行，因为新旧状态必然不同。

| 影响行数 | 可以得出的结论 | 下一步 |
|---:|---|---|
| 1 | 本次状态转换生效 | 提交后续事务内操作 |
| 0 | 没有满足完整条件的记录 | 区分重复请求、状态冲突或不存在 |
| 大于 1 | 单对象更新约束失效 | 中止事务并记录异常 |

零行不能直接等同于失败。请求可能已经成功过一次，第二次到达时记录早已是 `RELEASED`。如果系统把重复释放定义为幂等成功，就可以查询目标记录，确认身份和状态后返回“已释放”；如果记录已进入 `SHIPPED`，则应该返回状态冲突。

这种查询是为了解释没有生效的更新，不应把查到的任何状态都强行改成期望状态。

## 为什么 LIMIT 1 解决不了身份问题

给宽泛条件补上 `LIMIT 1`，确实可以限制修改数量，但无法证明被选中的那一行就是目标。对上面的三条预留来说，“只释放其中一条”和“释放第 101 条”有本质区别。

数量约束适合作为保护栏；身份约束才决定业务含义。如果业务天然要求某个组合唯一，例如一个订单对一个库存项只能有一条有效预留，应进一步评估唯一约束，让错误数据在写入时就被拒绝。

## 把副作用放进同一事务边界

释放预留通常还要增加可用库存。只有状态转换成功，库存才允许加回，而且两步应处在同一数据库事务中。重复请求因为第一步影响零行，不会再次增加库存。

最有价值的验证也由此明确：同一货品的其他预留不变；两个并发释放只有一个执行库存回补；已发货记录不能释放；重复请求得到稳定的业务结果。安全更新不是一句“条件写全”，而是让身份、状态转换和副作用共同形成可以检查的契约。
