# 外部数据匹配：在候选检索时兼容格式，在最终确认时保留严格条件

两个接口描述同一部影片，一个返回“远山”，另一个返回“远山（IMAX 2D）”。直接比较字符串会匹配失败；改成“只要包含远山就算匹配”，又可能把“远山 2”当成同一个对象。

这类问题在接口集成中很常见。外部名称既承担识别作用，又混入规格、格式、营销文案等展示信息。合适的处理方式，是让名称兼容只负责找候选，再用明确身份和结构化条件确认目标。

## 一个匹配过程，分成两个决策

以查询电影场次为例，调用方要找“远山、20:00、2 号厅、IMAX 2D”的一场放映。流程先通过影片列表找到影片标识，再查询该影片的具体场次。

第一步允许处理已知的展示差异，例如移除经过确认的放映格式后缀。第二步必须核对场次身份：影片、时间、影厅、放映格式都符合，才可以继续选择座位。

![候选检索与最终确认的两阶段匹配](博客公开附件/工程实践/外部数据匹配-在候选检索时兼容格式，在最终确认时保留严格条件.png)

宽松检索的目标是减少漏选，最终确认的目标是避免误选。这两个阶段使用不同强度的条件，才能同时获得兼容性和确定性。

## 归一化只处理已经理解的差异

“删除所有括号内容”看起来很通用，却可能删除真正的身份信息。例如“远山（导演剪辑版）”与普通版未必具有相同片长；“接口设计（第二版）”与第一版也不是同一本书。

因此，名称处理应采用有限规则：保留原始值，识别确定属于展示格式的尾缀，输出归一化名称，同时保留提取出的结构化属性。

```python
KNOWN_FORMATS = {'IMAX 2D', 'IMAX 3D', '2D', '3D'}

def normalize_name(raw):
    name = raw.strip()
    for left, right in [('（', '）'), ('(', ')')]:
        if name.endswith(right) and left in name:
            base, suffix = name.rsplit(left, 1)
            format_name = suffix[:-1].strip()
            if format_name in KNOWN_FORMATS and base.strip():
                return base.strip(), format_name
    return name, None
```

这段示例只处理一个已知尾缀，没有尝试修复任意文本。返回的格式属性不能丢弃：它不影响查找基础影片，却会参与最终场次确认。

| 输入名称 | 候选检索使用的名称 | 额外保留的信息 |
| --- | --- | --- |
| 远山 | 远山 | 无 |
| 远山（IMAX 2D） | 远山 | IMAX 2D |
| 远山 2 | 远山 2 | 无 |
| 远山（导演剪辑版） | 原样保留 | 未知后缀，不擅自删除 |

规则集中在适配层还有一个实际好处：外部接口变化时，可以定位到是哪一种表示差异，而不是在多个业务方法中寻找散落的 `replace` 和 `contains`。

## 候选多于一个时，歧义就是结果

即使基础名称完全一致，也可能出现重映版本、不同年份或同名作品。此时取列表第一项，会把外部返回顺序误当成业务判断。

候选数量本身应进入流程：没有候选，报告无法定位；只有一个候选，继续结构化确认；多个候选，使用年份、外部编码、版本等额外字段消歧。字段不足时返回“候选不唯一”，比默默选错更容易处理。

最终确认最好形成一个独立的判断，而不是依赖前面某一步已经“看起来相似”。以场次为例，可以比较：

```text
候选影片 ID == 已确认影片 ID
场次开始时间 == 目标开始时间
影厅 ID == 目标影厅 ID
放映格式 == 目标放映格式（请求指定时）
```

时间需要先统一时区与精度，影厅优先使用稳定 ID。条件缺失应形成明确的补充信息或拒绝路径，不能被默认相等吞掉。

## 回归用例应同时限制“放宽到哪里”

只验证“远山（IMAX 2D）能找到远山”，只能证明兼容规则生效。更重要的另一半，是证明“远山 2”不会因此混入，以及同名但时间、影厅不同的场次仍会被拒绝。

一组小而有代表性的样例就能覆盖关键边界：中英文括号属于正例，续集和未知版本属于反例，多个同名候选用于验证消歧，时间与影厅不匹配用于验证最终确认。

这种分层方式可用于商品规格、地址、设备型号和文件版本匹配。名称变化被限制在检索入口，真正决定动作的身份条件保持明确。兼容规则因而可以逐步增加，而不会把整条处理链路变成越来越难解释的模糊匹配。
