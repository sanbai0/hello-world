# 日志设计实践：用关联编号和阶段结果还原一次异步执行

用户点击“导出报表”，页面显示处理中，十分钟后仍没有文件。此时搜索一条 `export failed` 很难解决问题：它可能属于另一个用户，也可能只是第一次失败，第二次尝试已经成功。

异步系统中的日志需要回答的，不只是“这里发生过异常”，还包括哪项任务走到了哪一步、使用哪次尝试、结果由谁确认。设计日志时先确定这些问题，字段和输出位置通常就清晰了。

## 四种标识各有职责

以一个异步导出流程为例：接口受理请求，把任务放入队列；Worker 查询数据、生成文件、上传对象存储，最后更新任务状态。

| 字段 | 表示什么 | 生命周期 |
|---|---|---|
| requestId | 一次入口请求 | 一次 HTTP 调用 |
| jobId | 用户要完成的导出任务 | 从受理到最终结果 |
| attemptId | 一次执行尝试 | 每次重新执行都变化 |
| stage | 当前业务阶段 | 一次尝试内逐步变化 |

用户因网络问题重试提交，可能产生两个 `requestId`，但通过幂等键仍对应同一个 `jobId`。Worker 因临时读取失败重新执行，则保留 `jobId`，生成新的 `attemptId`。把这些标识混成一个字段，就很难区分“重复点击”和“后台重试”。

跨线程、跨队列时，标识需要作为消息字段显式传递。线程本地日志上下文方便输出，但不会因为提交了线程池任务就天然完成传播；任务结束后还应清理上下文，避免线程复用时把上一个任务的编号带入新日志。

## 记录状态变化，而不是每行代码

有价值的阶段可以是 `LOAD_DATA`、`RENDER_FILE`、`UPLOAD_FILE`。每个阶段在开始和结束时输出结构化事件，结束事件带结果、耗时以及必要的输出引用。

```json
{"jobId":"J-42","attemptId":"A-2","stage":"UPLOAD_FILE",
 "event":"started","timestamp":"2025-06-03T08:00:01Z"}
{"jobId":"J-42","attemptId":"A-2","stage":"UPLOAD_FILE",
 "event":"completed","outcome":"success","durationMs":840,
 "objectRef":"exports/J-42/report.csv","rows":1200}
```

`event` 和 `outcome` 分开，可以区分“开始执行”与“执行成功”。上传开始只证明代码发起了调用；上传成功应以存储接口确认或后续查询确认为依据。文件大小、行数这类摘要则帮助判断产物是否合理。

不需要在每个循环里输出“正在处理第 N 行”。那会让真正的状态变化淹没在噪声里。数据量很大时，可以使用低频进度记录，或只在阶段结束时输出累计数量。

## 让错误能够指导下一步

异常堆栈适合定位代码，错误类别适合决定处置。下面三种失败即使都发生在上传阶段，也应区分：

| 错误类别 | 含义 | 日志应补充的内容 |
|---|---|---|
| INVALID\_INPUT | 输入不符合约束 | 字段名、规则编号 |
| DEPENDENCY\_REJECTED | 依赖明确拒绝 | 状态码、外部请求编号 |
| OUTCOME\_UNKNOWN | 调用超时，结果待确认 | 目标对象键、确认入口 |

第三种尤其容易被误写成 `UPLOAD_FAILED`。超时只能说明本端没有及时得到结果；日志若直接断言远端失败，会诱导维护人员重新执行已经完成的操作。准确的事件名本身就是一种故障隔离措施。

## 从日志重建一条执行链

回到开头的例子，按 `jobId=J-42` 查询后，可能看到第一次尝试在读数据阶段失败，第二次上传成功，但任务最终状态写入失败。问题于是从“导出坏了”缩小为“产物已存在，结果状态未提交”。

这个判断依赖的是不同阶段各自留下的证据。若所有位置都输出同一句“任务处理成功”，就无法知道成功的是入队、生成、上传还是用户可下载。

异步日志也可能因缓冲和传输而乱序。时间戳用于观察时间，阶段与尝试编号用于解释因果；必要时增加任务内序号。不要仅凭日志文件的行序，认定多个进程里的事件先后关系。

日志最后还需要一条清楚的终态事件，包含任务状态和可用结果引用。它可以关联前面的阶段，却不能替代各阶段记录。面对“没有终态”的任务，阶段日志能指出最后确认的位置；面对“终态与用户体验不符”的任务，产物引用又能支持进一步核查。这样的记录结构让日志既适合搜索，也能服务告警和运行统计，而无需在排障时重新猜测字段含义。
