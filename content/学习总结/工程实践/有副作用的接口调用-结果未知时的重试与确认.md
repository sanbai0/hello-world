# 有副作用的接口调用：结果未知时的重试与确认

订单服务向支付渠道提交扣款请求。渠道已经扣款，响应却在返回途中丢失；客户端等待超时，捕获到一个网络异常。

此时最危险的代码，往往只有几行：

```java
try {
    return charge(order);
} catch (TimeoutException ex) {
    return charge(order); // 第一次是否生效，还没有得到答案
}
```

网络异常描述的是通信结果，不能单独证明业务动作没有发生。创建订单、扣减库存、发放权益等有副作用的调用，都需要给“结果未知”留出明确位置。

## 三种结果，需要三种后续动作

以订单 `ORDER-42` 的单次支付操作为例，接口适配层可以输出下面的结构：

| 结果 | 判断依据 | 自动流程 |
| --- | --- | --- |
| `SUCCEEDED` | 渠道明确确认目标交易成功 | 保存凭证，推进订单 |
| `FAILED` | 渠道明确拒绝且契约保证未扣款 | 按失败原因处理 |
| `UNKNOWN` | 超时、空响应、无法解释的返回 | 查询原交易，等待确认 |

“业务失败”不能简单等同于所有 HTTP 非 200 响应。网关错误可能发生在下游提交之后，状态码的解释必须服从渠道契约。即使 HTTP 200，响应缺少必要业务字段，也可能仍然无法得出结论。

## 重试的对象，比重试次数更重要

可以重试“查询原交易”，不等于可以重试“创建另一笔交易”。前者补充事实，后者可能新增资金动作。

在发出请求前，先持久化稳定的操作编号、业务订单号、金额和请求摘要。渠道支持幂等键时，同一操作的重发必须携带同一个键，并遵守其有效期和参数一致性要求。渠道不支持时，调用方更需要依赖原订单查询与明确的人工核实入口。

```java
PaymentOutcome pay(PaymentOperation op) {
    var response = gateway.submit(op.idempotencyKey(), op.request());
    var outcome = classify(response);
    if (outcome.isKnown()) return outcome;
    return confirmOriginalTrade(op); // 始终围绕原交易
}
```

这段示意代码省略了异常捕获与持久化细节，重点是未知分支不能重新生成交易身份。否则即使每一次调用都“带了幂等键”，不同的键仍可能被渠道视为两次合法支付。

## 查单成功，不等于查到了正确的成功

确认过程应核对业务对象、金额、币种和最终状态。查询接口返回成功，只能说明查单请求被处理；结果列表中有一笔成功交易，也不能说明它就是目标交易。

例如订单需要支付 128 元，查单返回 `ORDER-42`、128 元、已支付，才具备推进依据。若订单号不同、金额不同，或仍处于处理中，就不能转成业务成功。若渠道只返回交易流水号，应通过预先持久化的映射完成关联。

查单也要有时间预算。可以采用有限退避，并在每次查询前计算剩余时间：单次网络超时、退避等待和查询次数共同决定总耗时。达到确认期限后，任务进入待核实状态，后台对账或人工处理继续围绕同一操作编号展开。

## 未知状态要约束整条补偿链

一个常被遗漏的分支是自动取消。支付方法返回普通 `false` 后，上层可能立即取消订单、释放库存，再创建新订单重试。局部没有再次扣款，整条流程仍然产生了新的副作用。

因此未知结果应成为显式类型，传到状态机和补偿层：

```text
SUCCEEDED → 订单已支付
FAILED    → 可执行契约允许的失败处理
UNKNOWN   → 订单待确认，暂停重新支付与自动取消
```

待确认并不是永远挂起。系统应记录下一次确认时间、责任方和处理期限，使它可以被查询、告警、核销。确认成功后推进原订单；确认未生效后，才重新评估是否允许下一次业务尝试。

## 测试需要检查“没有多做什么”

这类逻辑适合用可控渠道桩模拟几个精确时序：扣款后响应丢失、前两次查单处理中而第三次成功、查到另一笔订单、确认窗口耗尽。

除了最终状态，还应断言：扣款操作身份保持不变；查单始终使用原标识；未知期间取消次数为零；重复成功通知不会再次推进订单或发放权益。

有副作用接口的可靠性，来自稳定的操作身份、清晰的结果分类和有边界的恢复路径。把未知保留下来，后续动作才有依据，也才能把一次网络抖动控制在一次业务操作之内。
