# 耗时任务 API 设计：幂等提交、状态轮询与重启收尾

一个报表生成任务需要两分钟，HTTP 网关却在三十秒后超时。客户端看到失败再次提交，后台可能已经同时生成两份报表。把超时时间调长可以缓解眼前问题，却无法回答更关键的几件事：第一次提交是否成功，后台是否还在执行，再次提交会不会重复，最后下载的是哪一次结果。

异步 API 的核心，是给任务一个稳定身份，让请求的寿命和执行的寿命分开。

## 提交的是一次意图，返回的是一个任务

调用方为同一次生成意图提供幂等键，服务端为已经受理的任务分配 `job_id`：

```http
POST /report-jobs
Idempotency-Key: report-demo-001
Content-Type: application/json

{"month":"2026-08","department":"sales"}
```

```json
{
  "job_id": "job-73",
  "state": "queued",
  "status_url": "/report-jobs/job-73"
}
```

响应可以使用 `202 Accepted`，明确表示已受理。若响应途中丢失，客户端带原幂等键重试，应得到同一个任务；若同一个键对应的月份变了，则返回冲突，不能把旧报表伪装成新请求的结果。

服务端因此需要保存“调用方范围、幂等键、规范化参数摘要、任务 ID”的绑定，并用数据库唯一约束处理并发提交。参数摘要应覆盖影响执行结果的字段，JSON 键的排列顺序等无关差异则应先规范化。

## 受理记录应先于执行承诺

如果接口先启动后台线程，再保存任务记录，进程在两步之间退出，客户端可能拿不到任何可以查询的身份。如果先保存记录，却使用没有恢复能力的内存队列，重启后又可能留下永远不执行的 `queued`。

可操作的设计是：在持久化存储中创建任务，再由可恢复的调度器认领待执行任务。对于单机服务，也可以让任务表兼任工作队列，由执行者原子认领；使用外部消息队列时，则需处理任务记录与投递之间的一致性。

![异步任务从受理到结果发布的生命周期](博客公开附件/工程实践/耗时任务-API-设计-幂等提交、状态轮询与重启收尾.png)

任务状态至少区分 `queued`、`running`、`succeeded`、`failed`。每个状态还应指导调用方的下一步，而不只是给页面换一种颜色。

| 情况 | 调用方动作 |
| --- | --- |
| 已排队或运行中 | 继续查询原任务 |
| 服务忙，尚未受理 | 按重试提示延后提交 |
| 需要重新登录 | 先恢复登录条件 |
| 执行失败且可重试 | 修复条件后创建新任务 |
| 成功且结果就绪 | 下载该任务绑定的结果 |

“服务忙”最好在受理边界清楚表达。如果已经建立了持久任务，就应返回该任务的状态，不能让客户端误以为未受理而创建一串新任务。

## 结果必须属于当前任务

报表生成器常把文件写入一个固定目录。如果下载接口只是取目录中“最新的文件”，本次生成失败后，用户可能下载到上一次报表。文件合法、接口成功，因果关系却已经断了。

任务记录应持有本次 `result_id` 或文件路径，并在结果完整写入、可供读取后才发布成功状态。可以先写临时文件，再原子替换到最终位置，避免下载到半个文件。

允许部分结果时，再单独提供 `result_available` 与完整性信息。不要用“文件存在”替代任务成功，也不要用“任务失败”掩盖所有已产生的有效内容。

```json
{
  "job_id": "job-73",
  "state": "succeeded",
  "result_available": true,
  "result_url": "/report-jobs/job-73/result"
}
```

## 重启需要结束失去执行者的状态

服务重启后，确认已失去执行者的 `running` 不能无限保留。单机服务可以根据旧进程已经退出进行收尾；多实例服务需要核对任务归属与执行租约，不能因为一个实例重启，就把其他实例仍在运行的任务标成失败。对于不能安全恢复的失主任务，可以转为 `failed`，错误码为 `worker_restarted`；支持断点续跑的任务，则需要根据检查点和新的执行权继续处理。

两种策略都可以成立，关键是接口契约明确。如果任务涉及外部副作用，不能仅凭进程消失就自动重做全部步骤，还要确认先前动作的结果。

轮询端同样需要节制：按照服务端建议间隔查询，网络错误重试原查询，终态后停止轮询。刷新页面可以恢复 `job_id`，无需重新提交生成请求。

设计完成后，可以用一次“提交响应丢失”与一次“执行中重启”检验契约。前者应仍然只对应一个任务，后者应最终给出可理解的状态。任务身份、状态与结果形成完整链路后，长任务才真正摆脱了对某一次 HTTP 连接的依赖。
