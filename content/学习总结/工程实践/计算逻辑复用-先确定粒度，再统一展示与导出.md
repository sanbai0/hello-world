# 计算逻辑复用：先确定粒度，再统一展示与导出

一个价格计算器最初只支持买一件商品。增加“购买数量”后，最直接的改法是把单件结果乘以数量。但只要存在满减、封顶、阶梯价或取整，数量就不再只是一个展示字段，它会改变计算对象。

以一个明确的规则为例：商品单价 100 元，每件优惠 30 元，但**每笔订单最多优惠 100 元**。购买四件时，两种算法的差异已经足够明显。

| 计算步骤 | 单件计算后乘四 | 先按整单计算 |
| --- | ---: | ---: |
| 商品总价 | 400 元 | 400 元 |
| 优惠金额 | 30 × 4 = 120 元 | min(30 × 4, 100) = 100 元 |
| 实付金额 | 280 元 | **300 元** |

问题不在乘法，而在封顶规则作用于订单。把订单拆成四件分别计算，相当于悄悄把一次优惠上限变成了四次。

## 为每条规则标注作用粒度

整理公式之前，先给输入和规则标注单位。这样可以提前发现哪些值能够相加，哪些必须放到整单阶段处理。

| 数据或规则 | 作用对象 | 处理位置 |
| --- | --- | --- |
| 商品单价、单件成本 | 一件商品 | 商品行 |
| 同款购买数量 | 一个商品行 | 商品行汇总 |
| 满减门槛、每单优惠上限 | 一笔订单 | 订单计算 |
| 运费最低收费 | 一个包裹 | 包裹计算 |
| 页面两位小数 | 展示值 | 输出格式化 |

“优惠金额”这样的名称太宽泛，容易让同一个变量同时承担门槛抵扣、实付抵扣和佣金计算三种职责。字段可以直接叫 `threshold_amount`、`payable_amount`，并把参与计算的项目写进规则定义。

例如某项活动明确规定，满 300 元的判断使用券前商品金额，积分只抵扣最终支付，那么先扣积分再判断门槛就会改变规则。计算顺序应来自规则的依赖关系，而不是来自代码里哪一步写起来更方便。

## 用整单层组织计算，用结果对象连接出口

单件引擎仍然可以复用。整单层先汇总数量与金额，执行订单级规则，再把需要分摊的金额分配到商品行，最后形成一份带明确单位的结果。

![从商品行到整单计算，再到统一结果](博客公开附件/工程实践/计算逻辑复用-先确定粒度，再统一展示与导出.png)

对于上述单品例子，使用“分”作为金额单位，核心计算可以很短：

```python
def compute_order(unit_price_cents, quantity):
    if quantity <= 0 or unit_price_cents < 0:
        raise ValueError('invalid quantity or unit price')
    subtotal = unit_price_cents * quantity
    discount = min(subtotal, 3000 * quantity, 10000)
    return {
        'quantity': quantity,
        'subtotal_cents': subtotal,
        'discount_cents': discount,
        'payable_cents': subtotal - discount,
    }
```

页面、导出和后续方案计算都读取这个结果。页面负责排版，Excel 导出负责列名和单元格格式，它们不再各自实现一次优惠计算。

复用结果对象比“都调用同一个工具模块”更具体。模块里如果同时有单件函数与整单函数，各个出口仍可能调用错；结果对象则可以用 `order_profit_cents`、`unit_profit_cents` 明确区分总额和单价，不让调用方靠字段位置猜测含义。

## 分摊要保住金额守恒

计算得到整单优惠后，订单明细可能还需要展示每件分摊值。这里又有一个容易忽略的边界：100 元分给三件商品，不能每件都写成 33.33 元后就结束，否则合计少了一分钱。

如果规则要求平均分摊，可以先做整数除法，再把余数按固定顺序分配：

```python
base, remainder = divmod(10000, 3)
allocated = [base + (i < remainder) for i in range(3)]
# [3334, 3333, 3333]，合计仍为 10000 分
```

如果规则要求按金额比例分摊，则需要另一个明确的分配策略，但同样要满足“明细合计等于整单总额”。分摊后的金额用于明细归属，不能再次触发一遍订单封顶。

## 验证要让非线性规则真正生效

只验证数量为一，几乎发现不了粒度错误。更有效的样例是：数量增加后刚好触及封顶、刚好跨过门槛，以及分摊后产生一分钱余数。

除了预期金额，还可以检查几条不会随页面变化的关系：商品小计等于单价乘数量；应付等于小计减有效优惠；明细分摊之和等于订单金额。同一输入和同一配置下，页面与导出的整单字段必须一致。

这种设计也让后续扩展更容易理解。增加多商品、包裹费用或阶梯优惠时，先找到规则所属的计算层，再扩展那一层的输入与输出。最终呈现的不只是一组数字，还有一套能够说明数字从哪里来的计算边界。
