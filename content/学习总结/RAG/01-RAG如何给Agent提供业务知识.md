# RAG 如何给 Agent 提供业务知识

## RAG 的基本过程

RAG 即检索增强生成：根据问题检索相关材料，把材料提供给模型，再让模型据此回答。

```text
用户问题 → 检索相关知识 → 把材料放入模型上下文 → 生成有依据的回答
```

这种做法在本次请求中补充模型能够使用的信息，不需要先把这批材料训练进模型参数。

检索来源可以是已有文档或其他可查询数据源，不必一开始就建设复杂的向量数据库系统。

## 为什么查到订单后还可能需要 RAG

订单工具回答“现在是什么状态”；业务规则告诉我们“这种状态应该怎样处理”。

下面全部是假设的教学数据与规则：

```json
{
  "order_id": "O001",
  "status": "processing",
  "waiting_minutes": 12,
  "receipt_received": false
}
```

Agent 查询订单后，发现还需要处理规则，于是请求：

```text
search_business_rules("订单处理中且未收到出票回执的处理规则")
```

检索工具返回：

```text
规则 ID：RULE-001
版本：demo-v1
内容：订单处理中超过 10 分钟，且尚未收到出票回执，
      应转人工核查；不得承诺具体出票时间。
```

模型可以结合状态和适用规则，建议转人工。只有程序执行转人工并取得成功依据后，才能告诉用户“已转人工”。

## 三类工具的分工

| 工具 | 提供什么 |
| --- | --- |
| 查询订单、出票回执 | 当前业务事实。 |
| 检索业务规则 | 处理规则、知识和说明。 |
| 创建人工工单 | 实际业务动作。 |

RAG 的检索结果不会自动完成业务操作。是否调用行动工具，仍由 Agent 流程提出请求、程序验证并执行。

简单 RAG 可以固定“先检索、后回答”；Agent 也可以根据任务决定何时检索、检索什么以及是否需要补查。并不是每个 Agent 都必须使用 RAG。

## 检索到了，也要判断能不能用

- 文档是否属于当前用户可以查看的范围？权限应在检索和返回环节落实，不能只交给模型自觉遵守。
- 是否适用于当前店铺、渠道、订单类型和时间？
- 版本是否有效，是否已被新规则替代？
- 材料是否足以回答问题，是否还缺少条件或例外？

缺少规则时应说明缺口或继续检索。回答引用了某个文档，也不代表引用支持它的全部结论，见 [[05-证据引用与结论核对]]。

## 后续学习顺序

1. 一份长文档怎样切成可检索的片段，并保留标题、来源和版本。
2. 关键词检索与语义检索分别适合什么问题。
3. 找到多个片段后，怎样筛选、排序和检查适用性。
4. 怎样检查漏检、错检，以及回答是否忠实于材料。
