# RAG 评估排错与检索循环

返回 [[学习索引]] · 前置 [[03-混合检索融合与重排序]]

## “有材料却答错”要分层检查

```text
材料在知识库里
≠ 进入检索候选
≠ 进入最终模型上下文
≠ 条件和例外完整且适用
≠ 模型正确使用材料
```

记录一次失败请求的候选、过滤结果、最终上下文和回答，再定位问题。日志访问和保存范围仍需符合数据权限要求。

| 排查环节 | 对应修复 |
| --- | --- |
| 版本、日期、渠道错 | 增加有效期和适用范围，按任务过滤；历史问题不一定使用最新规则。 |
| 正确材料在组装时漏掉或截断 | 检查实际模型请求，分配上下文预算，保留必要条款。 |
| 条件、例外分散或存在冲突 | 补父章节、合并关联段落、去重，按已确认规则处理优先级；不明冲突要说明。 |
| 材料充分清晰仍生成错误 | 约束回答结构、要求证据引用、核对结论；以相同样本比较提示词或模型。 |

“把正确材料放到最后”可以作为实验，但不能保证修复。先检查结构和完整性。

## 是否应该换更好的模型

人工提供一份简短、完整、无冲突的正确材料，再问同一问题：

- 能答对：优先排查检索与上下文组织。
- 仍答错：检查规则歧义、提示、输出要求，再比较模型能力。
- 稳定明确的条件判断：可以转成经业务确认、可维护版本的程序规则。

比较模型需使用同批问题和相同材料，同时观察正确率、成本与耗时。不能用一道恰好答对的题作结论。

## Hit@K 和 Recall@K

以下采用基于相关文档标注的定义：

- **Hit@K：前 K 条命中率。** 单题前 K 条至少包含一份相关文档记 1，否则记 0；再对样本求平均。
- **Recall@K：前 K 条召回率。** 单题为找回的相关文档数除以标注的全部相关文档数；跨题汇总时需说明使用的聚合口径。

某题需要 A 基本规则与 B 例外条款，前 5 条仅找到 A：

```text
单题 Hit@5 = 1
单题 Recall@5 = 1/2 = 50%
```

100 道有相关材料的问题中，80 道至少命中一份相关材料，整体 Hit@5 为 80%。命中不等于证据完整，检索指标也不等于回答正确率。

本来无答案的题应单独评估是否正确表示无法回答，不能直接套用分母为零的召回率。

某些评估框架还按参考答案中的事实检查证据覆盖，与基于文档 ID 的定义不同，报告指标时需说清口径。[Ragas Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)

## 怎样建立评估样本

先由业务人员确认少量代表性问题的所需证据与期望行为，逐步积累：正常问题、相似指标、例外条款、旧版本、无答案、无权限等。

分别检查检索覆盖、回答正确性、证据支持与拒答或澄清是否适当。模型辅助评分可以降低成本，但需要人工校准。

改切分、检索或模型之后，用同一批样本比较，并保留失败案例；不要只修一题而忽略其他题退步。

## Agent 检索不到时如何继续

先确认用对数据源：规则检索不能直接回答昨天实际发生了什么故障，业务事件要查记录工具。

工具设计示例：

```text
search_rules(query, channel, effective_date)
query_failure_stats(shop_id, start_time, end_time, group_by)
```

允许模型利用已取得的信息补充查询，例如由“出票失败处理”细化为“A 渠道 E\_TIMEOUT 回执超时处理”。不能凭空添加事实。

程序记录查询与返回证据 ID，并设置：

- 重复查询提醒或去重。
- 连续没有新证据时，调整数据源、请求澄清或停止。
- 缺少关键条件时询问用户。
- 调用次数、耗时和重试上限。

新证据是否有用，还要看它是否补上当前信息缺口。换几个近义词但一直返回同样材料，不算取得有效进展。
