# Agent 学习 07｜从出票分析到月报生成的完整案例

返回 [[学习索引]] · 前置 [[06-综合Agent入口与任务参数解析]]

自动出票系统接收订单后，会选择出票渠道、派发执行任务，再接收出票结果。一个订单可能经历多次调用或重试，所以“任务已经发送”“渠道接口返回成功”和“订单已经出票”分别描述不同的事情。

现在需要完成这样一项任务：

> 生成 9 月自动出票月报，与 8 月比较。重点解释出票成功率的变化，列出需要跟进的渠道问题，并按月报模板生成草稿。

这个场景把多渠道出票、异步任务和结果回传串在一起。下文数字、渠道名称和工具名均为教学示例，用来说明 Agent 的执行设计，不代表真实经营数据或已经上线的月报功能。

## 先确定月报到底在统计什么

“出票成功率下降了”看似明确，实际至少隐含了三个问题：哪些订单进入分母、怎样认定出票成功、失败重试算几次。

本例先确定以下口径：

| 统计项 | 本例约定 |
| --- | --- |
| 统计范围 | 已确认店铺范围内，由系统正式受理的有效出票订单；排除测试单和受理前取消单 |
| 月份归属 | 按受理时间归属月份，使用北京时间，不按日志写入时间分月 |
| 对比周期 | 2026 年 9 月与 8 月，比较月度总量和成功率 |
| 成功条件 | 已取得并校验票信息，且订单结果已确认为出票成功；发送任务成功不计作出票成功 |
| 去重单位 | 业务订单编号；一次订单重试三次，分母仍然只增加一单 |
| 数据截止 | 统一截至 10 月 3 日，本例两个订单批次均已取得最终结果，没有待确认订单 |
| 渠道分组 | 按订单固定归属渠道分组；重试或切换执行渠道不重复计单，实际执行渠道另用于调查 |

因此，本例的公式是：

```text
出票成功率 = 该月受理订单中最终出票成功的订单数 / 该月有效受理订单数
```

如果仍有待确认订单，报表需要单独列出数量和截止时间，不能把它们直接塞进“失败”。也不能拿“当月受理量”去除“当月完成量”：上月底接收、这个月才完成的订单会让两者不属于同一批样本。

口径确定后由程序固化为任务参数。模型可以提出需要澄清的条件，但不应为了让报告更顺畅而临时改变分母。

## 工具分工：统计交给程序，调查方向交给模型

| 示例工具 | 返回什么 |
| --- | --- |
| `resolve_ticket_metric` | 成功率定义、店铺范围、时间字段、状态映射和数据截止点 |
| `query_ticket_comparison` | 两个月的订单数、成功数、渠道拆分及按固定公式计算的差值 |
| `query_ticket_outcomes` | 指定渠道的最终结果分布，以及经过脱敏的异常订单样本 |
| `query_ticket_trace` | 按订单编号关联任务、尝试、阶段日志和最终回执 |
| `search_ticket_rules` | 适用的渠道处理规则、错误码说明与月报表述规范 |
| `load_report_template` | 按模板 ID 加载月报结构 |

这些工具提供受控的查询入口，不让模型自由拼接生产 SQL。程序校验权限和查询范围，返回数据覆盖情况、口径版本、统计截止点以及证据编号。

模板已知时直接按 ID 加载。只有需要查找规则解释时才检索文档，不必把每一次取数据都做成向量检索。

整个执行过程可以概括为：

```text
用户提出出票月报需求
    ↓
程序固定范围、口径和数据截止点
    ↓
查询两个月统计 → 模型识别值得调查的变化
    ↓
按渠道拆分 → 按最终结果拆分 → 关联任务日志
    ↓
模型组织解释 → 程序复算数字、核对引用和模板
    ↓
交付月报草稿，列出有明确对象的待核实事项
```

## 第一步：核实变化，再决定调查重点

程序查询并验证完整性后，得到证据 E001：

| 指标 | 8 月 | 9 月 | 变化 |
| --- | ---: | ---: | ---: |
| 有效受理订单 | 30,000 单 | 30,000 单 | 0 单 |
| 成功出票订单 | 28,500 单 | 26,400 单 | -2,100 单 |
| 未成功订单 | 1,500 单 | 3,600 单 | +2,100 单 |
| 出票成功率 | 95% | 88% | -7 个百分点 |

成功率从 95% 降到 88%，应写“下降 7 个百分点”。如果计算相对降幅，则是 `(88% - 95%) / 95% ≈ -7.37%`，两种说法不能混用。

随后按同一口径拆分渠道：

| 归属渠道 | 8 月成功 / 受理 | 9 月成功 / 受理 | 成功率变化 | 成功单量变化 |
| --- | ---: | ---: | ---: | ---: |
| A | 9,500 / 10,000 | 8,000 / 10,000 | 95% → 80% | -1,500 单 |
| B | 11,400 / 12,000 | 10,800 / 12,000 | 95% → 90% | -600 单 |
| C | 7,600 / 8,000 | 7,600 / 8,000 | 95% → 95% | 0 单 |

总成功率要用成功总数除以受理总数，不能直接平均三个渠道的成功率。本例两个月各渠道受理量保持一致，因此能清楚看到：减少的 2,100 单中，A 渠道占 1,500 单，约为 71.4%；B 渠道占其余 600 单。

模型据此把 A 作为优先调查对象，同时保留 B 的跟进项。这里确定的是**变化集中位置**，还没有证明 A 的哪一个故障造成了下降。

实际月报如果出现渠道占比、订单类型或月度天数变化，还需要分别分析订单结构和处理能力。不能把本例固定订单量下的结论直接套过去。

## 第二步：看新增了什么失败，而不只是寻找失败记录

查询 A 渠道的最终结果，得到证据 E002：

| A 渠道最终结果 | 8 月 | 9 月 | 变化 |
| --- | ---: | ---: | ---: |
| 出票成功 | 9,500 单 | 8,000 单 | -1,500 单 |
| 超过出票时限，已确认未出票 | 200 单 | 1,200 单 | +1,000 单 |
| 渠道明确拒绝出票 | 200 单 | 700 单 | +500 单 |
| 其他最终失败 | 100 单 | 100 单 | 0 单 |
| 合计 | 10,000 单 | 10,000 单 | 0 单 |

这些状态互斥，每个订单只归入一个最终结果。单次接口超时不等于订单最终失败：某次请求没收到响应，后续仍可能查询到出票成功。

这张表支持一个具体判断：A 渠道减少的 1,500 笔成功订单，对应增加了 1,000 笔超时未出票和 500 笔明确拒绝；其他失败数量没有增加。

如果只搜索到几条超时日志就写“下降全部由超时造成”，便跳过了两层核对：日志是不是同一订单的重复尝试，以及失败类型的变化是否足以解释全部差额。

## 第三步：从订单下钻到执行链路

模型可以继续提出两个查询方向：对新增的超时未出票订单分析集中时段，对新增的拒绝订单查看错误码分布。程序按已确定的店铺、渠道和月份执行查询。

订单与任务之间的关系需要保持清楚：

```text
业务订单 O-101              ← 月报按这个身份计数
  └─ 出票任务 T-501
       ├─ 尝试 1：请求超时
       └─ 尝试 2：查询到票信息
  └─ 最终结果：出票成功      ← 不能因第一条日志而算失败
```

再假设工具返回证据 E003：9 月 12 日的某个时段，A 渠道执行接口的响应超时明显增多，与部分最终超时未出票订单的尝试记录重合；该时段也存在渠道服务异常记录。

这可以支持“该时段存在值得进一步核对的渠道异常”，但还不能把全部 1,000 笔新增超时未出票都归因于这一事件。需要继续核对异常覆盖了哪些订单、是否存在队列等待或结果回传延迟，以及其他时段的订单为何失败。

固定归属渠道只是报表的分组维度。若订单执行中切换过渠道，调查时必须查看实际尝试链路，不能把所有问题都归到最初的渠道名下。

此时 Agent 的价值是根据已有结果选择下一步，而不是按固定脚本把所有日志扫一遍。补查仍没有新增证据时，应停止扩散查询，把具体缺口写进报告。

## 第四步：把证据组织成可以审核的月报

月报可以分为总体指标、渠道变化、异常调查和跟进事项。每一部分对应不同证据，不把数值统计、日志现象和业务规则混成一种结论。

| 证据 | 支持的内容 |
| --- | --- |
| E001：总体及渠道统计 | 成功率变化、下降集中在哪个渠道 |
| E002：最终结果分布 | 新增失败主要落在哪些结果类型 |
| E003：任务链路与异常记录 | 特定时段、订单与执行异常的关联 |
| E004：适用的出票规则 | 超时如何认定、结果何时确认、报告怎样表述 |

E004 由需要时调用的规则检索取得。它可以解释“什么算超时”，不能替代订单证据来证明某次超时确实发生。

依据上述材料，草稿的核心段落可以写成：

> 9 月有效受理出票订单 30,000 单，最终成功 26,400 单，成功率为 88%，较 8 月下降 7 个百分点。成功订单减少 2,100 单，其中 A 渠道减少 1,500 单，B 渠道减少 600 单，C 渠道持平。A 渠道新增失败主要为超时未出票和渠道明确拒绝，分别增加 1,000 单、500 单。部分超时订单与同期渠道接口异常存在关联，具体影响范围尚待按订单链路核实。

跟进事项也应写到可以执行的程度：核对 A 渠道异常时段的受影响订单集合，确认其最终结果；拆分新增拒绝订单的错误码；继续调查 B 渠道减少的 600 单。相比笼统写“加强监控、持续优化”，这样的月报能直接支撑下一步工作。

## 最后一步：验证报告，而不只是验证工具调用

程序可以确定性检查以下内容：

- 渠道受理量与成功量之和是否分别等于总体统计。
- A 渠道各最终结果是否互斥、合计是否为 10,000 单。
- 成功率、百分点差值和 71.4% 的贡献占比是否计算正确。
- 月份、店铺范围、数据截止点、指标版本和证据引用是否一致。
- 模板要求的章节是否齐全，最终失败是否混入了待确认订单。

自由文本还需要核对：引用是否支持整句话，是否把“同一时段发生”写成“已经证明导致”，是否把一次请求失败写成订单最终失败。可用模型辅助审阅，也可由人工确认；数字核对不能替代这一步。

任务状态最后分别记录：

```text
月度统计与口径校验：完成
渠道变化定位：完成
A 渠道结果拆分：完成
异常时段与任务链路调查：已形成阶段性证据
完整原因确认：待补充影响范围及 B 渠道调查
月报草稿：已生成，附可执行的跟进事项
```

如果交付要求是“含待核实事项的月报草稿”，此时可以完成；如果要求“确认成功率下降的全部根因”，任务仍有未完成部分。这个区别对应 [[04-结束条件与业务验收]] 中的验收边界。

这套设计里，程序守住订单身份、统计口径、权限范围和确定性计算；模型根据统计结果选择调查方向，并把不同层次的证据组织成解释。月报的可信度，来自每个数字能重算、每个判断能追溯、每个待办都有具体对象。
