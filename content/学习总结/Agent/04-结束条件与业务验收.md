# 结束条件与业务验收

返回 [[学习索引]] · 相关 [[01-Agent的组成与执行循环]]

## 谁决定结束

| 层面 | 谁判断 | 判断什么 |
| --- | --- | --- |
| 模型决策 | 模型 | 信息是否足够，建议回答、继续调用工具、澄清或转人工。 |
| 执行控制 | 程序 | 请求是否允许执行，是否达到预算，是否满足停止条件。 |
| 业务完成 | 程序规则或人工验收 | 问题是否解决，操作是否真正成功。 |

模型建议结束，程序可以检查后接受。程序也可以因为超时、异常或权限不足而停止，但这些停止都不意味着业务完成。

## 示例结束状态

这些是项目可以采用的业务状态名，不是所有 Agent 框架统一的协议。

| 状态 | 含义 |
| --- | --- |
| `completed` | 达到本次任务的完成标准。 |
| `waiting_for_user` | 等待用户补充店铺、日期或其他必要信息。 |
| `needs_human` | 当前能力或证据不足，需要人工处理。 |
| `failed` | 执行失败，当前流程无法完成。 |
| `budget_exceeded` | 达到调用次数、耗时等执行上限。 |

`needs_human` 表示需要人工，不代表已经成功创建人工工单。是否“已转人工”必须另外核对真实操作结果。

## 程序需要控制哪些预算

- 最大模型轮次和工具调用次数。
- 单次请求超时与任务总耗时。
- 对失败重试、无进展循环的限制。

这些限制由程序维护。提示词中的“不要无限循环”只是行为引导，不能替代执行限制。

## 回复用户之前检查什么

| 控制对象 | 检查内容 |
| --- | --- |
| 响应完整性 | 是否为空，是否被输出长度限制截断。 |
| 数字与状态 | 是否与查询、计算或操作结果一致。 |
| 行动承诺 | “已出票、已退款、已转人工”是否有成功依据。 |
| 交付格式 | 是否满足产品要求，是否意外暴露内部工具信息。 |

这些检查中，一部分可以通过结构化字段和规则完成，自由文本的含义可能还需要模型辅助或人工核对，不能假设程序能自动识别所有错误。

## “亲亲稍等，我帮你查一下”属于什么

它可以是查询前展示给用户的进度提示，前提是程序随后确实继续查询。

如果程序已经停止、也没有后续任务，这句话会让用户误以为查询仍在进行。最终回复需要明确结果、缺失信息或下一步处理方式。

## 验收应该对准用户目标

查询订单的工具执行成功，只证明这次查询按其契约完成。若用户问的是“为什么没出票”，还要判断取得的状态和回执能否解释该问题。

当证据只能证明“尚未收到回执”时，应说明这个事实和当前限制，不能自行升级成“出票方系统故障”。详见 [[05-证据引用与结论核对]]。
