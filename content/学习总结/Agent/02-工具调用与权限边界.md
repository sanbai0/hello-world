# Agent 学习 02｜工具调用与权限边界

返回 [[学习索引]] · 前一篇 [[01-Agent的组成与执行循环]]

## 执行函数之前，先过三个基本检查

| 边界 | 检查内容 | 不通过时 |
| --- | --- | --- |
| 工具是否存在 | 名称能否在当前允许使用的注册表里找到。 | 返回未知工具错误，记录调用信息。 |
| 参数是否合法 | 必填项、类型、日期格式、范围，以及必要业务规则。 | 返回明确的参数错误，允许在预算内修正。 |
| 身份是否有权限 | 当前用户能否访问对应店铺、组织、订单或执行操作。 | 拒绝执行，不泄露无权访问的数据。 |

这三个检查是基础，还需要按业务添加次数、耗时、操作前置条件等约束。

## 身份由程序取得

可信身份来自程序验证后的登录信息。模型可以提出“查 O001”，但不能通过填写某个 `user_id` 或角色字段来决定自己具有什么权限。

```python
# 示意代码：模型只提供业务查询参数。
args = validate_tool_arguments(model_arguments)
identity = get_verified_login_context()
authorize_order_read(identity, args["order_id"])
result = get_order(order_id=args["order_id"], identity=identity)
```

实际数据访问也要执行相应范围约束，避免只有入口检查、底层查询却能任意读取。

用户明确提出查询其他店铺，不等于其拥有访问权限。模型传入的店铺、组织或订单标识同样需要验证。

## 工具不存在时怎样处理

可以回传：“程序没有注册这个工具，可用工具为……”，让模型在允许的工具中重新选择，同时记录错误用于排查。

排查方向包括工具说明与注册表是否一致、名称是否变化、当前环境是否加载了工具。不要仅凭模型生成的函数名动态执行任意代码。

## 工具结果要能表达不完整和失败

下面是教学用结果结构，实际字段由项目自行定义：

```json
{
  "status": "partial",
  "data": [],
  "scope": {"shop_id": "S001", "date": "示例日期"},
  "coverage": {"complete": false, "reason": "下游查询超时"},
  "error": {"code": "UPSTREAM_TIMEOUT", "retryable": true}
}
```

- `success`：本次工具操作按约定完成，仍要看其业务含义和覆盖范围。
- `partial`：有部分结果，但不足以代表完整范围。
- `error`：本次操作失败。

**空列表加上不完整覆盖，不能推出“没有失败订单”。** HTTP 200 也只能说明接口层面的响应情况。

`retryable` 可以辅助决定是否重试，程序仍要检查剩余预算，以及该操作是否适合重复执行。

## 工具输出也是待核对的数据

程序应记录查询范围、结果完整性和结果来源，再供模型使用。工具返回的正文不应被当作能改变权限或系统规则的新指令。
