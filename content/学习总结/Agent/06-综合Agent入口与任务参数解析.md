# Agent 学习 06｜综合入口与任务参数解析

返回 [[学习索引]] · 后续 [[07-从变化分析到月报生成的完整案例]]

## 核心疑问：用户第一句话进来，就要求模型提取时间和指标吗？

只有明确进入分析业务时，才适合按分析任务的字段提取。“先提取这些字段”是一种业务流程设计，不是所有 Agent 必须遵守的通用步骤。

专门的月报页面已经确定业务类型，可以直接提取月报条件。综合聊天入口还需要处理问候、查订单、查规则、做报告等不同需求。

**综合入口与字段提取并不冲突：前者描述产品能力，后者描述某种任务内部的处理。**

## 综合入口怎样运行

```text
用户消息 + 会话状态 + 当前允许的工具
                ↓
          模型决定下一步
          ├─ 直接回答
          ├─ 请求补充信息
          ├─ 请求订单工具
          ├─ 请求知识检索工具
          └─ 请求月报任务工具
                         ↓
                  程序校验并执行
```

模型选择工具时可以同时提取参数，不一定需要额外调用一次模型做意图分类。例如：

```json
{
  "name": "prepare_monthly_report",
  "arguments": {
    "time_expression": "上个月",
    "org_name": "华北区域",
    "metric_name": "发电量",
    "comparison": null
  }
}
```

工具名和参数结构为教学设计。`comparison` 允许为空，前提是这个准备工具的参数契约明确允许；真正执行对比查询时仍需补齐必要条件。

程序也可以先调用一个意图分类步骤，再进入专门流程。是否分开取决于业务复杂度、可靠性与成本，不存在必须采用的唯一方式。

## 一句话里的字段从哪里来

用户：“帮我分析上个月华北区域发电量为什么下降，按公司月报模板生成报告。”

以业务时区为北京时间、当前日期为 2026-10-14 为例：

| 字段 | 来源 | 处理方式 |
| --- | --- | --- |
| 目标月份 2026-09 | “上个月”＋当前日期 | 程序解析，保存具体月份。 |
| 华北区域 | 用户原话 | 查询组织目录，匹配组织 ID 并检查权限。 |
| 月度发电量 | “发电量”＋月份范围 | 形成候选理解，再核对指标目录和口径。 |
| 单位 MWh | 用户没说 | 从指标定义取得；此处是假设单位。 |
| 环比 | 用户没说 | 查已确认的默认规范；没有规范则澄清。 |
| 对比月份 2026-08 | 目标月＋环比 | 确认环比之后才能计算。 |
| 公司月报模板 | 用户提出交付要求 | 根据业务配置找到模板 ID；不唯一时进一步确定。 |

“下降”是待核实的前提。它不能直接确定环比、同比或与计划值比较，也不证明数据真的下降。

## 将解析与补齐分开理解

模型首先提取明确表达的信息：

```json
{
  "time_expression": "上个月",
  "org_name": "华北区域",
  "metric_name": "发电量",
  "comparison": null,
  "output_requirement": "按公司月报模板生成报告"
}
```

随后由程序计算日期，查询组织、指标和模板目录。对默认值记录来源，不把业务默认值伪装成用户明确指定。

若对比方式仍未知，准备工具可以返回：

```json
{
  "status": "needs_clarification",
  "missing_fields": ["comparison"],
  "options": ["环比", "同比"]
}
```

模型据此询问用户。用户回复“同比”后，程序结合已保存的任务状态更新字段；其他条件保留。此时示例对比月份变为 2025-09。

不能每收到一句补充，就把它当作新任务，将之前字段清空。模型提出更新，程序检查后接受，详见 [[03-任务状态与动态计划]]。

## 本项目采用的学习设计

一个综合入口，由模型选择工具；关键业务流程由程序约束。先实现单 Agent 配多个工具，再按实际复杂度考虑路由或子 Agent。

综合能力不等于必须多智能体。官方框架同时提供工具循环、路由和固定流程等设计，没有依据据此断言某一种占据市场多数。
