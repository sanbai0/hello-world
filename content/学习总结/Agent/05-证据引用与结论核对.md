# 证据引用与结论核对

返回 [[学习索引]] · 相关 [[03-任务状态与动态计划]]

## 给工具结果分配证据 ID

程序可以把一次工具返回记为 E001，保存其任务、店铺、时间范围、口径、完整性和原始结果引用。模型输出结论时，附上使用的证据 ID。

程序随后可以检查：

- 引用是否存在于本次任务，以及当前用户是否有权使用。
- 证据店铺、时间、指标口径是否与结论一致。
- 数据是否覆盖所需范围。
- 数字是否能按约定公式重新计算。

**证据 ID 存在，只证明找得到这份材料，不证明它支持当前结论。** 还要检查结论与证据的关系。

## 数字怎样重算

按已经确定的指标定义，使用对应数据和公式计算。

假设本练习约定：

```text
出票成功率 = 指定范围内已成功出票的支付订单数 / 同范围支付订单数 × 100%
```

这是教学口径。真实系统还要明确退款、取消、重复记录、跨日出票和观察截止时间等处理方式。

若可信统计结果是支付订单 100 笔、成功出票 80 笔，程序算出的成功率就是 80%。无需遍历所有加减乘除组合。

```python
from decimal import Decimal

def success_rate(issued_paid_count, paid_count):
    if paid_count == 0:
        return None  # 无适用分母，不能直接写成 0%。
    return Decimal(issued_paid_count) / Decimal(paid_count) * 100
```

这里假设输入已经完成范围、完整性、去重及口径校验。实际可以由数据库聚合，也可以由程序处理原始记录；仅对错误的汇总数重新做除法，不能证明底层数据正确。

模型最好提出结构化结论，例如指标 ID、证据 ID、数值和单位，程序按指标 ID 找固定公式校验。不要直接执行模型给出的任意表达式或代码。

还应按约定的小数位和舍入规则比较结果。

## 百分比与百分点

失败率从 5% 变成 12%：

- 增加了 **7 个百分点**：12% − 5%。
- 相对增长 **140%**：(12% − 5%) / 5%。

两种表达含义不同，不能把“增加 7 个百分点”写成“相对增长 7%”。

## 自由文本结论怎样核对

先拆成短小、可检查的陈述。例如：

> 昨天失败率上升，主要由于出票方系统故障。

至少包含两个需要分别检查的判断：

1. 失败率是否真的上升？用同口径数据和计算结果核对。
2. 出票方系统故障是否是主要原因？需要能支持故障来源及影响范围的证据。

如果证据只有“80% 的失败订单记录了超时”，它支持的是超时现象。超时可能涉及下游、网络、排队或回执链路，不能据此直接确定故障责任方。

进一步可以核对订单与回执的关联、发生时间、请求链路、下游记录和其他可能解释。即使存在同一时间的故障记录，也仍要判断是否足以解释所讨论的订单和影响程度。

## 哪些核对适合程序，哪些需要辅助判断

| 内容 | 适合的检查方式 |
| --- | --- |
| 证据 ID、店铺、日期、单位 | 结构化字段与规则。 |
| 计数、比例、变化幅度 | 确定的指标公式与数据。 |
| “已退款”“已转人工” | 对应操作结果与业务状态。 |
| 文本证据是否支持某句话 | 模型辅助审核或人工审核。 |
| 复杂原因或责任判断 | 补充证据，必要时业务人员核实。 |

可以让审核模型针对每条结论给出 `supported`、`contradicted` 或 `insufficient`，并指出依据。但审核模型同样会误判，需要真实案例校准；不能把它作为绝对正确的裁判。

当证据不足时，可以补查、降低结论强度、明确标注假设，或回答“目前无法确认原因”。

## 忠实于材料与事实正确

回答能够从检索材料中推导出来，说明它与材料相符；如果材料本身过时或错误，回答仍可能错误。

因此，要同时关注来源、适用范围、版本和证据完整性。这也是 [[01-RAG如何给Agent提供业务知识]] 中检索业务规则需要考虑的问题。
