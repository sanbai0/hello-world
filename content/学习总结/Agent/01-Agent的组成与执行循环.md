# Agent 学习 01｜组成与执行循环

返回 [[学习索引]] · 下一篇 [[02-工具调用与权限边界]]

## 五个组成部分

| 部分 | 作用 |
| --- | --- |
| 模型 | 判断需要什么信息、选择工具、根据结果决定下一步；提出调用请求。 |
| 工具 | 提供具体能力，例如查询订单、查询出票回执、计算成功率。 |
| 上下文与状态 | 保留用户目标、历史消息、取得的数据和当前进度。 |
| Agent 循环 | 组织“模型请求 → 程序执行 → 结果回传 → 模型继续判断”。 |
| 执行约束 | 由代码限制工具、权限、调用次数、耗时等。 |

模型可以通过远程 API 调用，也可以来自本地模型服务。真正执行函数的是外部程序。

## 一次工具调用怎样发生

```text
用户：帮我看看这个订单为什么还没出票
  ↓
程序把问题、允许使用的工具说明和必要上下文发给模型
  ↓
模型提出 get_order(order_id="O001")
  ↓
程序检查工具、参数和权限
  ↓
程序执行查询，把结果回传给模型
  ↓
模型根据结果决定：继续查回执、询问用户，还是准备回答
  ↓
程序检查结束条件与回复，再交付给用户
```

这里的 `get_order` 是教学工具名，不是模型自带能力。开发者需要实现函数，并在工具注册表中建立名称和函数的对应关系。

## 模型怎么知道有哪些工具

程序给模型工具名称、用途描述和参数格式，例如：

```json
{
  "name": "get_order",
  "description": "查询指定订单的状态",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {"type": "string"}
    },
    "required": ["order_id"],
    "additionalProperties": false
  }
}
```

这是简化的工具定义示例；具体 API 外层封装取决于接入协议。函数实现和数据库凭证不需要交给模型。

## assistant 不一定是给用户看的话

常见消息角色：

| 角色 | 在执行过程中的含义 |
| --- | --- |
| system | 程序提供的总体要求和行为说明。 |
| user | 用户提出的问题或补充信息。 |
| assistant | 模型的输出，可能是文字，也可能包含工具调用请求。 |
| tool | 程序执行工具后返回的结果。 |

在采用 `tools/tool_calls` 的接口中，程序读取结构化的 `tool_calls` 字段识别调用请求，解析工具名和参数。工具返回时用对应的 `tool_call_id` 关联请求。

如果响应既有文字又有工具调用，应按调用协议处理工具请求，不能仅凭“有文字”就判定完成。没有工具调用的文字也只是候选回复，还可能需要检查是否为空、被截断或缺乏依据。

用户最终看到的文字可以由模型生成、由程序模板生成，或两者结合。固定数字和状态可以由程序直接填入模板。

## 提示词与程序各负责什么

提示词可以告诉模型“只查询当前用户允许查看的订单”，但实际查询函数仍必须验证身份和范围。模型是否遵守提示，不能成为权限控制的唯一依据。

Agent 并不要求每次先生成显式计划。简单问题可能一次工具调用就能回答；复杂问题才更需要 [[03-任务状态与动态计划]]。
