## 发文

继续在原有“学习总结”中写作，建议属性：

```yaml
---
title: 一篇笔记的标题
description: 一两句话概括本篇内容。
created: 2026-10-19
publish: true
tags:
  - Go
  - 排障
cssclasses:
  - pinned
---
```

置顶 `cssclasses: [pinned]` 可选，首页最多两篇。Syncer 保留 `cssclasses`，会过滤任意 `pinned`，不要为此打开全部 frontmatter。标签可以多选。

打开命令面板 `Quartz Syncer: Open publication center`，查看新增、修改和撤稿，选择这次要发布的笔记，点击 `PUBLISH SELECTED CHANGES`。插件直接更新 GitHub，Actions 自动构建并发布。没有保存即上传或定时发布。

发布过程中让 Obsidian 保持在前台，等它显示成功提示；测试时后台窗口曾出现较长等待，唤到前台后提交完成。进度条走完不代表 GitHub 已经收到提交；网站还需等待 Actions 的 Build、Deploy 成功。

日常流程就是“原库写好 → 发布中心点发布 → 网站自动更新”，不增加本地发布副本审核、附件许可清单或额外 Git 推送步骤。安装与首次设置已完成，真实插件及 Pages 的新增、更新、改名和撤稿已经验收；日常不需要 Codex、ChatGPT 或 AI API。

## 公开内容范围

- 公开文章里只引用愿意公开的图片和附件。原版会自动上传被引用的媒体，不要求给每张图片另设 publish，也无需在博客项目维护图片清单。
- 双链、嵌入会保留目标名称；被发布的关联文章可能被 Quartz 展开。写作时不要引用不愿公开的文件，原版没有额外的自动隐私拦截。
- 原始简历、同步凭据、令牌、`.obsidian` 和整个原库仍不属于公开范围。此要求不因取消额外审核而改变。
- `npm run audit:content` 与 `public-content.policy.json` 保留为可选的严格诊断工具，沿用前一方案的限制，可能把正常发文标为不符合旧规则；不参与预览、构建或 Actions，日常发文无需使用或维护它们。

## 更新、改名和撤稿

**更新**：修改原来的同一路径笔记，在发布中心选 Changed notes；插件更新同一仓库路径，不产生新文章。避免只为了改显示标题而改文件路径。

**改名/移动**：默认网址跟随文件路径。发布中心会出现新路径的 Unpublished 和旧路径的 Deleted。先发布新路径，再选中旧路径执行 Unpublish/Delete；发布按钮本身不会替你删除旧副本。旧网址默认失效；如需保留先设计别名/重定向。此次未改真实笔记。

**撤稿**：在原文把 publish 设为 false/去掉标记，再到发布中心选中 Deleted 中的旧副本，执行 Unpublish/Delete。也可从 Published 中撤下已公开文章，但保留 publish:true 会使它下次重新成为发布候选。仅去标记不代表网页已下线。无需删除原文，避免影响原同步。核对撤稿路径，先处理其他文章对它的链接；孤立图片单独处理，不能删掉仍被引用的图。Actions 完成后实际检查旧网址和搜索索引。

撤稿不清除 Git 历史、浏览器或搜索引擎缓存。敏感信息不能先上传再删除；若已上传，必须另行处置历史和相关凭据。

## 首页分类与排序

首页提供“全部、工程实践、Agent 学习、RAG 学习”分类入口。“全部”和“工程实践”按文章日期倒序；Agent、RAG 分类按文件名前的数字编号从小到大排列，并显示“按章节顺序”。因此首页全部列表可能先显示 Agent 07、08，切换到 Agent 分类后从 01 开始阅读。

分类根据目录自动识别：工程文章放在“学习总结/工程实践”，Agent、RAG 分别放在对应系列目录。正常发布后会自动加入分类，无需手动维护列表；新增系列在 blog.settings.ts 的 learningSeries 中配置。分类地址可以直接分享，刷新或返回时保留所选分类。未启用 JavaScript 时仍可阅读完整日期列表。

## 文章底部导航与评论

文章底部的导航自动生成，不用在 Obsidian 手写链接。Agent、RAG 等已配置系列按文件名前面的数字编号排列，显示“上一章 / 下一章”；普通文章按创建日期从早到晚衔接，显示“上一篇 / 下一篇”，不混入系列文章。首篇和末篇只显示存在的相邻文章，只有一篇时不显示翻页。首页、归档、关于和标签页不显示文章翻页。

评论接入采用 Quartz 社区 Comments 插件与 giscus，位置在文章导航之后，使用中文、明暗主题和 iframe 延迟加载；评论保存在指定公开仓库的 GitHub Discussions 中。发表评论需要 GitHub 登录，日常 Obsidian 发布流程不变。

首次启用需要仓库管理员在 GitHub 开启 Discussions，并安装官方 giscus App，仅选择 sanbai0/hello-world。App 权限为 Discussions 读写、Metadata 只读，不需要 Contents 写入。现有发布令牌没有 Administration 权限，不能代替这次账号安装确认。

用户已决定暂缓启用评论，当前保持关闭，也未将评论插件加入部署依赖；避免公开网站显示错误评论框及增加安装耗时。repoId、中文、主题及关联方式配置已准备。未来启用时先将官方兼容提交 8a76dfafc0742c1903212c4fc8e15f6fb5f9e99f 加入插件锁文件并安装，在 quartz.config.yaml 中填入 Announcements 分类的 categoryId，再将 enabled 改为 true。新版 1.0.0 的共享类型声明与本项目 Quartz 5.0.0 冲突，不因此升级整站。

评论按 pathname 关联文章：修改 title 不改变关联；改名、移动文件或更换网站路径时，应检查并迁移对应 Discussion 的映射，旧评论不会自动跟随新网址。撤稿不会自动删除 GitHub Discussions 中的评论。不要在评论中填写私密信息。

## 部署排障

1. 仓库 → Actions → 最新 Deploy blog，查看失败步骤。Build 和 Deploy 均成功后，还要打开实际公开 URL。
2. 地址失败：核对账号/仓库与 `baseUrl`，分支为 `main`。
3. 文章没有出现：确认原笔记 publish 为 true、来源在学习总结、发布中心已选中，并核对插件目标仓库及分支为 main。普通发文不会运行旧的逐文件许可检查。
4. 安装/构建失败：本地先 `./scripts/blog.ps1 install` 再 `build`，保持两个锁文件一并提交，不盲目升级全部插件。
5. Pages 权限失败：Source 必须是 GitHub Actions，部署环境允许 main。工作流 build 只读 Contents，deploy 使用 Pages write 和 ID token write，不需要个人令牌写入 Actions。
6. 仍显示旧网页：比对提交 SHA、Actions 部署记录、实际网址及缓存，不能只看进程或构建成功。
7. 文章图片或子目录双链异常：本站已在 Quartz 构建端加入来源目录路径兼容，保持 `vaultPath=学习总结`、`contentFolder=content/学习总结`。不要为修复链接而手动复制、改写原文或修改插件；站点维护时可用 `node scripts/test-syncer-link-paths.mjs` 做一次真实构建回归。

免费 github.io 不保证中国大陆访问稳定。一次成功打开网页也不能代表大陆多网络访问稳定，本次不承诺速度和稳定性。
